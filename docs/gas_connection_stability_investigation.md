# GAS接続不安定性 調査ノート(T5-A103)

- 調査日: 2026-08-22 / 担当: `architect`
- 対象: 2026-08-22のPR #5(T5-B12)/PR #6(T5-B23)検証で`integration_test/smoke_test.dart`が4回連続FAILした件
- 調査方法: **静的診断のみ**(`sheets_service.dart`・`smoke_test.dart`・`gas/Code.gs`・関連画面/プロバイダの読解)。実機再現は行っていない。

---

## 1. 結論(完了条件1: 原因の切り分け)

**(a)GAS側の一時的不安定性が引き金だが、真因は(c)アプリ側/テスト側の実装欠陥**。(b)エミュレータ固有の問題である証拠は無い。

4つの失敗様相はすべて「1つの根本欠陥 + 症状の分岐」で説明できる。

### 真因1: `SheetsService`にタイムアウトもリトライも無く、GETの例外を握り潰す

- `lib/services/sheets_service.dart:35` — `_client.get(...)`に`.timeout()`が無い。`_postData`(同727行)も同様。リトライ処理はファイル全体に存在しない(`lib/services/`配下にも`.timeout(`は1件も無い)。
- 同81〜84行 — `catch (e)`で**全例外を握り潰して`return []`**する。呼び出し側から見ると「通信失敗」と「データが0件」が区別できない。
- `SheetsService`は`sheetsServiceProvider`(同755行)で単一インスタンス化され、`http.Client()`(同25行)を長期保持する。報告された`ClientException: Connection closed before full header was received`は、**Dartの`http`クライアントがkeep-aliveで保持していたアイドル接続をサーバ側が先に閉じた後に再利用した**ときに出る典型的なエラーで、リトライ1回で通る種類の障害(この因果は既知の`http`パッケージの挙動に基づく推定であり、本調査ではパケットレベルの裏付けは取っていない=**仮説**)。
- 起動〜ダッシュボード表示で`lib/providers/data_providers.dart`の12プロバイダがほぼ同時にGETを撃つため、1本でも当たれば失敗する確率が上がる(接続数の多さは失敗確率の増幅要因。**未検証**)。

### 真因2: 握り潰した`[]`が「壊れたレコードの保存」に化ける(失敗2・4=件数不変の説明)

1. `pouring_steps`のGETが失敗 → `_fetchData`が`[]`を返す → `pouringStepsProvider`は**`AsyncData([])`**(エラーにならない)。
2. `lib/screens/brew_recipe_screen.dart:415`の`stepsReady = stepsAsync.hasValue && !stepsAsync.hasError`が**true**になり、030のメソッド選択が有効化される(2026-08-21のこの修正は「読込中の誤選択」は防ぐが、**例外が握り潰されている以上`hasError`は永遠にfalse**なので今回のケースには効かない)。
3. メソッドを選んでも`_workingSteps`が空 → `_finishAndEvaluate()`(同341〜358行)で`totalTime = 0`のまま031へ。
4. 031で保存自体は成功(SnackBar「登録しました」)するが、002の一覧は`logs.where((l) => l.methodId.isNotEmpty && l.totalTime > 0)`(`lib/screens/log_list_screen.dart:90`)で**この記録を除外**する。
5. 結果: **保存は成功・一覧件数は不変(178→178 / 179→179)**。テストの失敗様相と完全に一致する。
6. 副作用: 失敗した4回の実行で、`totalTime=0`のゴミ記録が**本番`coffee_data`シートに残っている可能性が高い**(テストは削除しない)。要確認。

### 真因3: タイムアウト不在が`pumpAndSettle`の10分タイムアウトに化ける(失敗3=12分の説明)

- GETがハングすると`coffeeRecordsProvider`はloadingのまま → 002は`CircularProgressIndicator`(無限アニメーション、`log_list_screen.dart:180-183`)を出し続ける → `pumpAndSettle`は永久にsettleせず**既定10分**で例外。前段の所要時間を足すと実測「12分」と整合する(**機序としては十分だが、どのフレームで止まったかのログ確認はしていない=仮説**)。

### 失敗1(履歴0件)の説明

`coffee_data`のGET失敗 → `[]` → `validLogs.isEmpty` → 「抽出履歴がありません」表示 → `smoke_test.dart:235`で失敗。これも真因1の直接の帰結。

### テストコード側の独立した欠陥(GASが健全でも落ちる)

- `smoke_test.dart:96` — メソッドを`methodOptions.first`で選ぶだけで、**注湯ステップ(duration>0)を持つメソッドかを確認していない**。先頭のメソッドがステップ未設定なら、GASが健全でも`totalTime=0`となり一覧件数が増えない。ファイル冒頭の前提条件コメント(15〜16行目)が要求している条件を、テスト自身が検証していない。
- `smoke_test.dart:232-241` — 保存後に002へ遷移し`pumpAndSettle`1回で件数を数えている。`ref.invalidate(coffeeRecordsProvider)`(`brew_evaluation_screen.dart:259`)後の**再取得完了を待っていない**ため、再取得が遅いと件数0(loading中)で判定してしまう。同ファイル内には`_pumpUntil`というポーリング用ヘルパが既にあるのに、ここでは使われていない。

### (b)エミュレータ固有説について

エミュレータのNAT越しではアイドルTCP接続が切られやすく顕在化しやすい、という説明は成り立つが、**同じ欠陥はWeb/実機でも起こりうる**(Chromeはブラウザのfetchを使うため症状の出方は異なる)。「エミュレータだから」で片付けると、実ユーザー環境で同じゴミレコード生成が起き続ける。エミュレータ固有と結論づける証拠は本調査では得られていない。

## 2. 完了条件2: Sheets→ローカルDB移行はGAS接続に依存するか

**製品としての移行処理はGASに依存しない。ただしテストゲートは依存し続ける。**

| 観点 | 依存 | 根拠 |
|---|---|---|
| driftのスキーマ移行(T5-B12、`stepByStep`) | **非依存** | 端末内SQLiteのスキーマ操作のみ。ネットワークを使わない |
| `LocalDbService`(T5-B13) | **非依存** | `DataService`の別実装。公開版は空のローカルDBから始まる |
| 画像のローカル保存(T5-B14) | **非依存** | `path_provider`で端末内に保存 |
| エクスポート/インポート(T5-B15) | **非依存** | JSONファイル経由(`docs/local_db_schema_design.md` §7・§423) |
| personal(Sheets)のデータを公開版へ持ち込む場合 | **一部依存** | エクスポートJSONは`?sheet=`のGET生JSONと同形(同 §423)。読み出し1回だけGASを通るが、手動・再実行可能な一回性操作でリトライで吸収できる |
| **T5-B13以降の終了条件「`integration_test`スモークが通る」** | **依存** | スモークは`lib/main.dart`(personal版=Sheets/GAS)を起動する。GASが不安定な限り、B13以降も同じ理由でゲート不通過になる |

したがって「移行作業そのものがGASに依存するから早期解決必須」ではないが、**ゲート条件として毎ループ足を引っ張るため、解決の優先度は高いまま**である。

## 3. 完了条件3: 対処方針

実装が必要。後続タスクとして **T5-A104(アプリ側、M)** と **T5-A105(テスト側、S)** を起票した(詳細な完了条件はマスタープラン §3 トラックAの各行)。方針の要点のみ以下に記す。

1. **GETにタイムアウト(20秒)+リトライ(最大3試行、指数バックオフ)を入れ、全試行失敗時は`[]`を返さず例外を投げる。** 握り潰しをやめることで`hasError`分岐が初めて機能し、真因2の「壊れたレコードの保存」が構造的に起きなくなる。
2. **POSTはリトライしない**(`appendRow`が冪等でないため、再送は重複行を生む)。タイムアウト(30秒)のみ追加し、既存どおり例外を再スローしてUIにエラーを出す。
3. **スモークテストは「ステップを持つメソッド」を選び、保存後の一覧反映をポーリングで待つ。**
4. **運用**: 失敗4回で本番`coffee_data`に`totalTime=0`のゴミ記録が入っている可能性がある。ユーザーがSheetsを目視し、あれば削除する(削除操作はユーザー確認が必要なため自動化しない)。

### 実装しない選択肢とその理由

- 「GAS側にLockService/リトライを入れる」: `gas/Code.gs`に排他制御は無いが、今回の失敗はGAS実行時間やロック競合ではなく**接続レイヤ**で起きている(`Connection closed before full header was received`)。GAS側改修の費用対効果は低い。必要になれば別途調査する。
- 「スモークからGASを外す」: T5-B13完了後に公開版(ローカルDB)基準のスモークへ切り替えるのが本筋だが、personal版の回帰検証をGAS込みで行う価値は残るため、本タスクでは切り離さない。
