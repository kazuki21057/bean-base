# コードベース構成方針: web個人版 と Android公開版 の分離

作成日: 2026-08-07 / 決定: **1コードベース + エディション分離**(ブランチ分岐しない)
関連文書: [`コスト試算.md`](./コスト試算.md) / [`収益化アイデア.md`](./収益化アイデア.md)

## 1. 決定と背景

BeanBase には性質の異なる2つの配布形態が生まれる。

| | **personal**(web) | **public**(Android) |
|---|---|---|
| 用途 | 作者個人の常用 | 一般公開 |
| データ | Google Sheets(GAS) | 端末ローカルDB |
| AI | 自分のGeminiキーを設定画面に入力 | サーバ経由 or 自前キー(段階次第) |
| 画面 | 全画面 + debug/mock | 一般ユーザー向けのみ |
| 広告・課金 | なし | あり(将来) |

**これをブランチで分けない。** 理由は §4。代わりに「エディション」という1つの軸で出し分ける。

### 却下した案
- **長期ブランチ `android`**: ローカルDB化でデータ層が大きく分岐するため、web側の改修を cherry-pick するたびにコンフリクトが常態化する。「統計処理は順次アップデート」という要件と最も相性が悪い
- **リポジトリ分離**: 共通コード(models / statistics / math / widgets)が23,000行の大部分を占め、二重管理になる

## 2. 仕組み(3層)

### 層1: エントリポイントの分離

```
lib/main.dart         → personal 版(現状のまま。web の常用を壊さない)
lib/main_public.dart  → public 版
```

```bash
flutter run -d chrome                                   # personal(従来どおり)
flutter run -t lib/main_public.dart -d <android>        # public
flutter build appbundle -t lib/main_public.dart --dart-define=EDITION=public
```

### 層2: エディション設定オブジェクト

`lib/config/app_edition.dart` を新設し、**差分をすべてここに集約**する。

```dart
enum Edition { personal, public }

class AppEdition {
  final Edition kind;
  final Set<AppScreen> enabledScreens;  // 出す画面の集合
  final bool useLocalDb;                // false=Sheets / true=ローカルDB
  final AiKeyMode aiKeyMode;            // ownKey / proxy
  final bool showAds;
  final bool enableSubscription;
}
```

`const bool.fromEnvironment('EDITION')` を併用すれば、**public ビルドから personal 専用画面をツリーシェイキングで落とせる**(アプリサイズと誤操作の両方に効く)。

### 層3: 既存の切り替え点への接続

このリポジトリには接続点が**すでに揃っている**。新規に足場を作る必要がない点が、この方針を選ぶ最大の根拠。

| 差分 | 接続先 | 状態 |
|---|---|---|
| データバックエンド | `dataServiceProvider`(`lib/providers/data_providers.dart`) | **既存**。CLAUDE.md 記載どおり一行で差し替え可能 |
| 画面の有無 | `screenRegistry`(`lib/routing/screen_registry.dart`)、`AppScreen.topLevelTabs`(`lib/routing/app_screen.dart`) | **既存**(Cycle 20 T1-1a で整備済み) |
| ナビの項目 | `destinations:`(`lib/layout/main_layout.dart:73, 92`) | **既存**。`enabledScreens` でフィルタするだけ |
| AIキーの取得元 | `AiAnalysisService`(`lib/services/ai_analysis_service.dart`) | 要改修(1箇所) |
| 広告・課金 | 新規 | public のみ |

## 3. 差分の置き場所ルール(最重要)

この方針が破綻するかどうかは、**差分をどの粒度で置くか**だけで決まる。

**やってよい**
- 画面まるごとの出し分け → `enabledScreens` に入れる/入れない
- サービス実装の差し替え → provider 1箇所で分岐
- 文言・定数・上限値の差 → `AppEdition` のフィールド
- 同じ画面でレイアウトが大きく違う → **画面ファイルを2つに分け、中の Widget を共有する**

**やってはいけない**
- ウィジェットの中に `if (edition == Edition.public)` を量産すること

前者は「差分が1箇所に集まる」形、後者は「差分がコード全体に散る」形。**後者を始めた瞬間に、ブランチ分岐より保守が悪化する。**

### 撤退条件(正直に)
- ウィジェット内のエディション分岐が20箇所を超えたら、その画面群を別実装へ切り出す
- それでも破綻するなら、共通部分を `packages/bean_core` に切り出すパッケージ分割へ移行する(**ブランチ分岐ではなく、モジュール分割で解く**)

## 4. なぜブランチ分岐より良いか

1. **「統計処理は順次アップデート」という要件が自動で満たされる。** 統計・数理コード(`lib/services/statistics_service.dart`、`lib/services/math/`)は共通のまま両エディションに乗る。ブランチ分岐だと更新のたびに cherry-pick が必要
2. **共通コードが大部分。** models / statistics / math / widgets は両者で同一。分岐させる意味のあるコードはデータ層と一部画面だけ
3. **cherry-pick とコンフリクト解消の運用が丸ごと不要**になる
4. **副作用として web 側にも利点がある。** ローカルDB実装が「選べるバックエンド」として web からも使えるため、Sheets 障害時の退避やオフライン利用の手段になる

## 5. リスクと緩和

| リスク | 緩和 |
|---|---|
| main に未完成の public 用コードが入り、web の常用が不安定になる | `enabledScreens` から外す + compile-time const で web ビルドから排除。personal 版の動作に触れない限り影響ゼロ |
| 検証コストが2倍 | `flutter analyze` / `flutter test` は共通。ビルド確認だけ2種類。`flutter build web` と `flutter build appbundle -t lib/main_public.dart` を検証フローに追加する |
| エディション分岐の入れ忘れで、public に個人用画面が出る | `enabledScreens` を**ホワイトリスト方式**にする(既定は非表示、明示的に許可した画面だけ出す) |

## 6. 既存コードとの適合

`lib/screens/debug/`(`firebase_test_screen`、`screen_gallery_screen`)と `lib/screens/mock/` は、**すでに「personal でしか使わない画面」の実例**である。したがって:

- これらを `enabledScreens` の最初の適用対象にすれば、**低リスクでパターンを検証できる**
- 万一分岐が壊れても、失われるのは開発用画面だけで実害がない

## 7. 移行タスク分解

Android 化本体(ローカルDB・課金)の前に、足場だけ先に入れる。各タスクは独立して検証可能。

| ID | 内容 | 完了条件 | 規模 |
|---|---|---|---|
| E-1 | `lib/config/app_edition.dart` 新設、`lib/main_public.dart` 追加 | 両エントリポイントが**同一の動作**で起動する(差分ゼロの状態を先に作る) | 小 |
| E-2 | `enabledScreens` を `screenRegistry` / `main_layout.dart` の `destinations` に接続。ホワイトリスト方式 | public 版で debug/mock 画面が出ない。personal 版は従来どおり全画面 | 小〜中 |
| E-3 | `dataServiceProvider` を `AppEdition.useLocalDb` 経由にする(実装はまだ `SheetsService` のみ) | personal 版が従来どおり Sheets で動く | 小 |
| E-4 | `AiAnalysisService` のキー取得を `AppEdition.aiKeyMode` 経由にする | personal 版のAI機能が従来どおり動く | 小 |

**E-1 で「差分ゼロの2エントリポイント」をまず作るのが要点。** 足場だけ先に通しておけば、以降のAndroid化タスクは既存動作を壊さずに積める。

E-1〜E-4 完了後、[`コスト試算.md`](./コスト試算.md) §4 の Phase A(Android化)へ進む。なお同 §2-3 の2施策(`maxOutputTokens` 設定・画像リサイズ)は**エディションに関係なく両方に効く**ため、この足場より先に実施してよい。

## 8. ブランチ運用

- **`main`** = 単一の正。web(personal)版はここから常用する
- Android 化の各タスクは**通常どおり作業ブランチを切って main へマージ**する。長期ブランチは作らない
- 本文書の3ドキュメントは main に置く(どちらのエディションの作業中でも参照するため)
