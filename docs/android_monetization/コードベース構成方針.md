# コードベース構成方針: web個人版 と Android公開版 の分離

作成日: 2026-08-07 / 決定: **1コードベース + エディション分離**(ブランチ分岐しない)
関連文書: [`コスト試算.md`](./コスト試算.md) / [`収益化アイデア.md`](./収益化アイデア.md)

## 1. 決定と背景

BeanBase には性質の異なる2つの配布形態が生まれる。

| | **personal**(web) | **public**(Android) |
|---|---|---|
| 用途 | 作者個人の常用 | 一般公開 |
| データ | Google Sheets(GAS) | 端末ローカルDB |
| AI | 自分のGeminiキーを設定画面に入力 | サーバ経由 or 自前キー(段階次第) |
| 画面 | 全画面 + debug/mock | 一般ユーザー向けのみ |
| 広告・課金 | なし | あり(将来) |

**これをブランチで分けない。** 理由は §4。代わりに「エディション」という1つの軸で出し分ける。

### 却下した案
- **長期ブランチ `android`**: ローカルDB化でデータ層が大きく分岐するため、web側の改修を cherry-pick するたびにコンフリクトが常態化する。「統計処理は順次アップデート」という要件と最も相性が悪い
- **リポジトリ分離**: 共通コード(models / statistics / math / widgets)が23,000行の大部分を占め、二重管理になる

## 2. 仕組み(3層)

### 層1: エントリポイントの分離

```
lib/main.dart         → personal 版(現状のまま。web の常用を壊さない)
lib/main_public.dart  → public 版
```

```bash
flutter run -d chrome                                   # personal(従来どおり)
flutter run -t lib/main_public.dart -d <android>        # public
flutter build appbundle -t lib/main_public.dart --dart-define=EDITION=public
```

### 層2: エディション設定オブジェクト

`lib/config/app_edition.dart` を新設し、**差分をすべてここに集約**する。

```dart
enum Edition { personal, public }

class AppEdition {
  final Edition kind;
  final Set<AppScreen> enabledScreens;  // 出す画面の集合
  final bool useLocalDb;                // false=Sheets / true=ローカルDB
  final AiKeyMode aiKeyMode;            // ownKey / proxy
  final bool showAds;
  final bool enableSubscription;
}
```

`const bool.fromEnvironment('EDITION')` を併用すれば、**public ビルドから personal 専用画面をツリーシェイキングで落とせる**(アプリサイズと誤操作の両方に効く)。

### 層3: 既存の切り替え点への接続

このリポジトリには接続点が**すでに揃っている**。新規に足場を作る必要がない点が、この方針を選ぶ最大の根拠。

| 差分 | 接続先 | 状態 |
|---|---|---|
| データバックエンド | `dataServiceProvider`(`lib/providers/data_providers.dart`) | **既存**。CLAUDE.md 記載どおり一行で差し替え可能 |
| 画面の有無 | `screenRegistry`(`lib/routing/screen_registry.dart`)、`AppScreen.topLevelTabs`(`lib/routing/app_screen.dart`) | **既存**(Cycle 20 T1-1a で整備済み) |
| ナビの項目 | `destinations:`(`lib/layout/main_layout.dart:73, 92`) | **既存**。`enabledScreens` でフィルタするだけ |
| AIキーの取得元 | `AiAnalysisService`(`lib/services/ai_analysis_service.dart`) | 要改修(1箇所) |
| 広告・課金 | 新規 | public のみ |

## 3. 差分の置き場所ルール(最重要)

この方針が破綻するかどうかは、**差分をどの粒度で置くか**だけで決まる。

**やってよい**
- 画面まるごとの出し分け → `enabledScreens` に入れる/入れない
- サービス実装の差し替え → provider 1箇所で分岐
- 文言・定数・上限値の差 → `AppEdition` のフィールド
- 同じ画面でレイアウトが大きく違う → **画面ファイルを2つに分け、中の Widget を共有する**

**やってはいけない**
- ウィジェットの中に `if (edition == Edition.public)` を量産すること

前者は「差分が1箇所に集まる」形、後者は「差分がコード全体に散る」形。**後者を始めた瞬間に、ブランチ分岐より保守が悪化する。**

### 撤退条件(正直に)
- ウィジェット内のエディション分岐が20箇所を超えたら、その画面群を別実装へ切り出す
- それでも破綻するなら、共通部分を `packages/bean_core` に切り出すパッケージ分割へ移行する(**ブランチ分岐ではなく、モジュール分割で解く**)

## 4. なぜブランチ分岐より良いか

1. **「統計処理は順次アップデート」という要件が自動で満たされる。** 統計・数理コード(`lib/services/statistics_service.dart`、`lib/services/math/`)は共通のまま両エディションに乗る。ブランチ分岐だと更新のたびに cherry-pick が必要
2. **共通コードが大部分。** models / statistics / math / widgets は両者で同一。分岐させる意味のあるコードはデータ層と一部画面だけ
3. **cherry-pick とコンフリクト解消の運用が丸ごと不要**になる
4. **副作用として web 側にも利点がある。** ローカルDB実装が「選べるバックエンド」として web からも使えるため、Sheets 障害時の退避やオフライン利用の手段になる

## 5. リスクと緩和

| リスク | 緩和 |
|---|---|
| main に未完成の public 用コードが入り、web の常用が不安定になる | `enabledScreens` から外す + compile-time const で web ビルドから排除。personal 版の動作に触れない限り影響ゼロ |
| 検証コストが2倍 | `flutter analyze` / `flutter test` は共通。ビルド確認だけ2種類。`flutter build web` と `flutter build appbundle -t lib/main_public.dart` を検証フローに追加する |
| エディション分岐の入れ忘れで、public に個人用画面が出る | `enabledScreens` を**ホワイトリスト方式**にする(既定は非表示、明示的に許可した画面だけ出す) |

## 6. 既存コードとの適合

`lib/screens/debug/`(`firebase_test_screen`、`screen_gallery_screen`)と `lib/screens/mock/` は、**すでに「personal でしか使わない画面」の実例**である。したがって:

- これらを `enabledScreens` の最初の適用対象にすれば、**低リスクでパターンを検証できる**
- 万一分岐が壊れても、失われるのは開発用画面だけで実害がない

## 7. 移行タスク分解

Android 化本体(ローカルDB・課金)の前に、足場だけ先に入れる。各タスクは独立して検証可能。

| ID | 内容 | 完了条件 | 規模 |
|---|---|---|---|
| E-1 | `lib/config/app_edition.dart` 新設、`lib/main_public.dart` 追加 | 両エントリポイントが**同一の動作**で起動する(差分ゼロの状態を先に作る) | 小 |
| E-2 | `enabledScreens` を `screenRegistry` / `main_layout.dart` の `destinations` に接続。ホワイトリスト方式 | public 版で debug/mock 画面が出ない。personal 版は従来どおり全画面 | 小〜中 |
| E-3 | `dataServiceProvider` を `AppEdition.useLocalDb` 経由にする(実装はまだ `SheetsService` のみ) | personal 版が従来どおり Sheets で動く | 小 |
| E-4 | `AiAnalysisService` のキー取得を `AppEdition.aiKeyMode` 経由にする | personal 版のAI機能が従来どおり動く | 小 |

**E-1 で「差分ゼロの2エントリポイント」をまず作るのが要点。** 足場だけ先に通しておけば、以降のAndroid化タスクは既存動作を壊さずに積める。

E-1〜E-4 完了後、[`コスト試算.md`](./コスト試算.md) §4 の Phase A(Android化)へ進む。なお同 §2-3 の2施策(`maxOutputTokens` 設定・画像リサイズ)は**エディションに関係なく両方に効く**ため、この足場より先に実施してよい。

## 8. ブランチ運用

- **`main`** = 単一の正。web(personal)版はここから常用する
- Android 化の各タスクは**通常どおり作業ブランチを切って main へマージ**する。長期ブランチは作らない
- 本文書の3ドキュメントは main に置く(どちらのエディションの作業中でも参照するため)

## 9. E-2(T5-B2)実装仕様 — `enabledScreens` の接続

2026-08-18に`architect`が決定。夜間ループがこのタスクで2回スタックしたため、設計判断を確定させた版。**implementerはこの節だけ読めば実装できる**。

### 9.1 前提となるコードの事実(調査で裏を取ったもの)

夜間ループが「9画面(ダッシュボード・ログ一覧/詳細・各マスタ詳細)をpublicから外すと中核ナビが消える」と判断して停止したが、**この前提は誤り**だった。根拠:

| 事実 | 裏付け |
|---|---|
| `buildScreenWidget()`の呼び出し元は**1箇所だけ** | `lib/screens/debug/screen_gallery_screen.dart:34`。`lib/`全体をgrepしても他に無い |
| 実アプリのトップレベルタブは`screen_registry`を**通らない** | `lib/layout/main_layout.dart:32-47`の`_screenFor`が別の解決表を持ち、`DashboardScreen`/`LogListScreen`等の**実データ版**を返す |
| 詳細画面も`screen_registry`を**通らない** | 各一覧から実クラスを直接push。例: `lib/screens/bean_list_screen.dart:150`→`BeanDetailScreen`、`lib/screens/log_list_screen.dart:173`→`LogDetailScreen`、`lib/screens/dashboard_screen.dart:187,263` |
| `lib/screens/mock/`のWidgetは**ギャラリー経由でしか到達できない** | 上記3点の帰結。実データ版の`bean_detail_screen.dart`等は別途存在する |

したがって:
- モック由来の9 IDを`enabledScreens`から外しても、**実ナビは1画面も失われない**(想定した実害は存在しない)。
- 逆に外すと`AppScreen.topLevelTabs`に含まれる`dashboard`・`logList`がナビのフィルタで消え、**ホーム・履歴タブが無くなる**。これが唯一かつ現実の実害。
- `docs/android_monetization/コードベース構成方針.md` §6が言う「debug/mockを最初の適用対象にする」は、**ギャラリー導線を閉じること**で達成される(モック画面はギャラリーからしか到達できないため)。

### 9.2 決定(D1〜D5)

- **D1(`enabledScreens`の意味を確定)**: `enabledScreens`は「**その`AppScreen` IDがこのエディションで到達可能か**」を表す。`screen_registry`がその画面に対して現在モックを返すかどうかは**無関係**。モックかどうかはCycle 20の実装進捗の産物であり、エディション方針とは別の軸。
- **D2(publicの値は現状維持)**: `kPublicEdition.enabledScreens = kAllAppScreens`のまま変更しない。ホワイトリストの**仕組み**をT5-B2で通し、**中身の絞り込みは絞る理由ができた時に行う**(§9.5)。
- **D3(開発者向け画面は別フィールドで遮断)**: `AppEdition`に`showDebugScreens`(bool)を追加し、personal=`true` / public=`false`とする。`FirebaseTestScreen`・`ScreenGalleryScreen`は`AppScreen` enumに**IDを持たない**ため`enabledScreens`では表現できない。`AppScreen`にIDを足す案は採らない(マスタープラン§4の画面インベントリの定義を汚し、`app_screen.dart`のコード体系〈001/002/…〉に開発用画面が混ざるため)。「文言・定数・上限値の差は`AppEdition`のフィールドに置く」という§3のルールに合致する。
- **D4(`isScreenImplemented()`とは連動させない)**: 理由3点。(1)関心が違う——実装進捗 vs エディション方針。(2)連動させると、Cycle 20の無関係なコミット(モック→実装の差し替え)が**レビュー機会なしにpublicビルドの画面構成を変えてしまう**。エディションの画面構成は明示的な変更としてdiffに現れるべき。(3)`isScreenImplemented()`はギャラリー表示専用であり、publicにはそのギャラリーが無い。なお`isScreenImplemented()`は現状`=> true`固定で、実際にはモックの画面にも「UIモック」チップを出す実装と噛み合っていない(全画面にチップが出る)。**これはT5-B2のスコープ外**——別途Sタスクとして扱う。
- **D5(エディション分岐の物理的な置き場所)**: 分岐は次の**3箇所のみ**に置く。`main_layout.dart`(ナビ項目)・`screen_registry.dart`(可視画面の列挙)・`settings_screen.dart`(デバッグセクション)。ウィジェット内に`if (edition.kind == Edition.public)`を増やさない(§3の禁止事項)。

### 9.3 実装タスク(implementer向け)

**1. `lib/config/app_edition.dart`** — フィールド追加。

- `AppEdition`に`final bool showDebugScreens;`を追加(`enableSubscription`の次)。コンストラクタも`required this.showDebugScreens,`を追加。
- docコメント: `/// 開発者向け画面(lib/screens/debug/)への導線を出すか。public版はfalse。`
- `kPersonalEdition`: `showDebugScreens: true,`
- `kPublicEdition`: `showDebugScreens: false,`
- `kPublicEdition.enabledScreens`は`kAllAppScreens`のまま**変更しない**。ただし94-95行目のコメントを次に差し替える:
  ```
  /// public(Android)版。enabledScreensは現時点では全画面を許可する(T5-B2で決定、
  /// 根拠は コードベース構成方針.md §9.2 D2)。開発者向け画面の遮断は
  /// showDebugScreens=false で行う。
  ```

**2. `lib/routing/screen_registry.dart`** — 可視画面の列挙関数を追加(末尾、`isScreenImplemented`の下)。

```dart
/// このエディションで到達可能な画面の一覧(ホワイトリスト適用後)。
/// enum の宣言順を保つ。
List<AppScreen> visibleScreens(AppEdition edition) =>
    AppScreen.values.where(edition.enabledScreens.contains).toList();
```
- import追加: `import '../config/app_edition.dart';`(このファイルは`always_use_package_imports`をignore済みなので相対importでよい)。`app_edition.dart`は`app_screen.dart`しかimportしていないため循環importにならない。
- `buildScreenWidget()`の`switch`は**触らない**(網羅的switchであることが「enumに足したらcaseを足し忘れるとコンパイルエラー」というガードになっているため。`docs/exploration_status_design.md`§8)。

**3. `lib/screens/debug/screen_gallery_screen.dart`** — ホワイトリスト適用。

- `StatelessWidget`→`ConsumerWidget`に変更(`import 'package:flutter_riverpod/flutter_riverpod.dart';`追加、`build(BuildContext context, WidgetRef ref)`)。
- `final screens = visibleScreens(ref.watch(appEditionProvider));`を作り、`itemCount: screens.length` / `final screen = screens[index];`に差し替える(`AppScreen.values`の直接参照をやめる)。

**4. `lib/layout/main_layout.dart`** — `destinations`のフィルタ。**ここが唯一の要注意点**。

`navIndexProvider`の値は現在`AppScreen.topLevelTabs`のindexだが、フィルタ後は「**表示中のタブ配列`visibleTabs`のindex**」という意味になる。`navIndexProvider`は`main_layout.dart`内でしか読み書きされていない(grep確認済み)ため、この意味変更の影響は同ファイル内に閉じる。

`build`(55行目〜)の冒頭を次の形にする:
```dart
final selectedIndex = ref.watch(navIndexProvider);
final edition = ref.watch(appEditionProvider);
final visibleTabs = AppScreen.topLevelTabs
    .where(edition.enabledScreens.contains)
    .toList();
// enabledScreens の縮小で selectedIndex が範囲外になると
// NavigationBar/NavigationRail の assert に触れるため必ずクランプする。
final safeIndex =
    (selectedIndex >= 0 && selectedIndex < visibleTabs.length) ? selectedIndex : 0;
```
- `NavigationRail`/`NavigationBar`の`selectedIndex:`は`safeIndex`を渡す。
- 2箇所の`for (final screen in AppScreen.topLevelTabs)`を`for (final screen in visibleTabs)`に変更。
- `onDestinationSelected`は`_navigateToIndex(index, visibleTabs)`を呼ぶ形にし、`_navigateToIndex(int index, List<AppScreen> tabs)`は`_screenFor(tabs[index])`を使う。
- **`visibleTabs.isEmpty`のガード**: 空の場合はナビを描かず本文だけ表示する。具体的には`isMobile`分岐の前に
  ```dart
  if (visibleTabs.isEmpty) {
    return Scaffold(body: child);
  }
  ```
  を置く(現状どちらのエディションでも空にならないが、将来`enabledScreens`を縮めた時に静かに落ちるのを防ぐ)。
- `_screenFor`の`default:`分岐は現状のまま維持する。

現時点では両エディションとも`visibleTabs == topLevelTabs`なので、**personal/publicとも実行時の挙動は変わらない**(既存の`test/screen_transition_test.dart`もそのまま通るはず)。

**5. `lib/screens/settings_screen.dart:414-441`** — デバッグセクションをpublicで隠す。

- `FormSection(icon: Icons.bug_report_outlined, title: 'デバッグ', ...)`全体を、親の`children`リスト内でcollection-ifで包む:
  ```dart
  if (ref.watch(appEditionProvider).showDebugScreens) ...[
    const SizedBox(height: 8),
    FormSection(icon: Icons.bug_report_outlined, title: 'デバッグ', children: [ ... ]),

  ```
  (直前の`const SizedBox(height: 8)`〈413行目〉も一緒に包む。publicで余白だけ残らないようにするため)
- この`FormSection`は`_SettingsScreenState`(`ConsumerState`)の`build`内にあるので`ref`はそのまま使える。
- import追加: `import '../config/app_edition.dart';`
- **注意**: 「画像一括インポート」もこのデバッグセクション内にある。public版では同時に消えるが、public版は当面Sheets運用でないためこれで問題ない(将来必要になったら別セクションへ移す)。

### 9.4 検証観点

- **効いたと言える判定**: 上記受入テスト6件が全パス。特にケース5が落ちる場合、フィルタがハードコードのままか、`navIndexProvider`のクランプが無い。
- **回帰**: `flutter test`全パス(特に`test/screen_transition_test.dart`・`test/settings_screen_test.dart`・`test/settings_screen_overflow_test.dart`)。`flutter analyze`新規issueゼロ。`flutter build apk --release -t lib/main_public.dart`成功。
- **手動**: personal(`flutter run -d chrome`)で設定画面に「デバッグ」セクションが**ある**こと、タブが5つ出ること。

### 9.5 いつ`kPublicEdition.enabledScreens`を絞るか(将来の手順)

以下のいずれかが起きた時に、この節を更新した上で絞る。**それまでは絞らない**。

1. **public専用のUI(トラックB P2)が入り、public版に出したくない画面が具体的に決まった時。**
2. **personal専用の画面が新設された時**(例: Sheets運用専用の管理画面)。新設時点で`kPublicEdition.enabledScreens`から外す。
3. **リリース前の最終確認**(トラックB終盤)。この時点で「public版に出す画面」を1画面ずつ棚卸しし、`kPublicEdition.enabledScreens`を`kAllAppScreens`参照から**明示的な列挙**へ書き換える。

なお`kAllAppScreens`(`app_edition.dart:49-81`)は手動列挙であり、`AppScreen`に画面を足しても自動では追従しない(T5-B1の`adversary`指摘のMinor)。§9.3のテストケース1・2(`length == AppScreen.values.length`)が**この追従漏れを検知するガードを兼ねる**。

## 10. E-4(T5-B4)実装仕様 — AIキー取得の`AppEdition`経由化

2026-08-18に`architect`が決定。`proxy`モードの実体(Cloud Run中継)がT5-B40/T5-B41まで存在しないため、夜間ループがスタックした。

### 10.1 前提となるコードの事実

- `AiAnalysisService`(`lib/services/ai_analysis_service.dart`)は**キーを取得しない**。5メソッド(`extractBeanInfoFromImage`・`fetchStoreInfo`・`interpretRegression`・`analyzeComponents`・`analyzeComponentsDeep`)が`apiKey`を引数で受け取るだけ。
- `gemini_api_key`を`SharedPreferences`から直接読み書きしているのは**6ファイル**:

| ファイル:行 | 用途 |
|---|---|
| `lib/screens/settings_screen.dart:116` | 読み(設定画面の初期表示) |
| `lib/screens/settings_screen.dart:123` | 書き(設定画面の保存) |
| `lib/widgets/statistics/regression_section.dart:636,640` | 読み+未設定ならダイアログ入力→書き |
| `lib/widgets/statistics/pca_detail_panel.dart:206,210` | 同上 |
| `lib/widgets/statistics/pca_scatter_plot.dart:232,238` | 同上 |
| `lib/screens/create/store_create_screen.dart:110,114` | 同上 |
| `lib/screens/create/bean_create_screen.dart:290,294` | 同上 |

- 5つの呼び出し元は`ref.read(aiAnalysisServiceProvider)`でサービスを取得している(`aiAnalysisServiceProvider`は`ai_analysis_service.dart:610`)。

### 10.2 決定(D6〜D9)

- **D6(スコープを`ownKey`に絞る)**: T5-B4は「**キー取得経路を`AppEdition.aiKeyMode`経由の1箇所に集約する**」までとし、`proxy`モードは**明示的なプレースホルダ**(専用例外+日本語文言)にする。理由: 中継サーバの仕様(URL・認証方式)はT5-B41で初めて決まる。今それを推測で実装すると、T5-B41で必ず捨てることになる。public版は未リリースのため`proxy`が動かないことによる実害はゼロ。
- **D7(`AiAnalysisService`の`apiKey`引数は変えない)**: 5メソッドのシグネチャは現状維持。理由: (1)`AiAnalysisService`が純粋なままだとテストしやすい(`test/store_ai_fetch_test.dart`等が既にキーを直接渡している)、(2)`proxy`モードで実際に差し替わるのは**キーではなく通信経路**(Gemini直叩き vs 中継サーバ)なので、キー引数を消しても将来の`proxy`実装には役立たない。T5-B41では`AiAnalysisService`の内部に「送信先」の抽象を入れる別の改修が必要になる——**T5-B4はそこに踏み込まない**。
- **D8(集約先は新規の`AiKeyService`)**: `lib/services/ai_key_service.dart`を新設し、`gemini_api_key`という文字列リテラルが**このファイル以外に存在しない**状態にする。
- **D9(ダイアログは統合しない)**: 5つの呼び出し元が持つ「未設定ならキー入力ダイアログを出す」UIは各ファイルに残す。統合はUIリファクタでありT5-B4(Sサイズ)のスコープ外。T5-B4で置き換えるのは`prefs.getString/setString`の**2行だけ**。

### 10.3 実装タスク(implementer向け)

**1. `lib/services/ai_key_service.dart`(新規)**

```dart
/// SharedPreferences 上のGemini APIキーの保存先キー。
/// この文字列を他のファイルに書かないこと(T5-B4で集約した)。
const String kGeminiApiKeyPrefsKey = 'gemini_api_key';

/// AIキーがこのエディションでは取得できないことを表す例外。
class AiKeyUnavailableException implements Exception {
  final String message;
  const AiKeyUnavailableException(this.message);
  @override
  String toString() => message;
}

/// AIキーの取得・保存を [AppEdition.aiKeyMode] に応じて切り替える。
class AiKeyService { ... }

final aiKeyServiceProvider = Provider<AiKeyService>((ref) =>
    AiKeyService(ref.watch(appEditionProvider).aiKeyMode));
```

`AiKeyService`のAPI(この3つだけ):

| メンバ | `ownKey`時の挙動 | `proxy`時の挙動 |
|---|---|---|
| `Future<String?> readKey()` | `SharedPreferences`から`kGeminiApiKeyPrefsKey`を読み、`trim()`して空文字なら`null`を返す | `AiKeyUnavailableException`をthrow |
| `Future<void> saveKey(String key)` | `trim()`して保存。`debugPrint('[Antigravity] Action: Gemini APIキーを保存')` | `AiKeyUnavailableException`をthrow |
| `bool get requiresUserKey` | `true` | `false` |

- `proxy`時の例外文言(**UIにそのまま出る日本語**、実文言):
  `'この版のAI機能はサーバ経由で提供されます。現在準備中のためご利用いただけません。'`
- `proxy`時は例外throwの直前に`debugPrint('[Antigravity] AIキー取得: proxyモードは未実装(T5-B41で中継サーバを実装予定)');`を出す。
- `readKey()`の`null`は「**未設定**」を意味し、「取得できない」(=例外)とは区別する。既存の呼び出し元はこの区別に依存する(未設定→入力ダイアログを出す)。

**2. 呼び出し元6ファイルの置き換え**(挙動は変えない)

- `prefs.getString('gemini_api_key')` → `await ref.read(aiKeyServiceProvider).readKey()`
- `prefs.setString('gemini_api_key', x)` → `await ref.read(aiKeyServiceProvider).saveKey(x)`
- 使わなくなった`final prefs = await SharedPreferences.getInstance();`と`shared_preferences`のimportは、**そのファイル内で他に使われていない場合のみ**削除する(`settings_screen.dart`は他の設定も読んでいる可能性があるので要確認)。
- **`proxy`での例外ハンドリング**: 5つのAI起動箇所(`regression_section.dart:634`の`_run`、`pca_detail_panel.dart:204`の`_run`、`pca_scatter_plot.dart:230`の`_handleAiAnalysis`、`store_create_screen.dart:109`付近、`bean_create_screen.dart:289`付近)で、キー取得を`try`で囲み
  ```dart
  } on AiKeyUnavailableException catch (e) {
    if (!mounted) return;   // Stateless側は context.mounted を使う
    ScaffoldMessenger.of(context).showSnackBar(SnackBar(content: Text(e.message)));
    return;
  }
  ```
  とする。SnackBar本文は例外の`message`(上記の日本語文言)をそのまま出す。
- **`settings_screen.dart`**: `_loadSettings`(113行目)は`readKey()`が例外を投げうるので`try`/`catch (AiKeyUnavailableException)`で囲み、catch時は`_apiKeyController.text = ''`のままにする。さらにAPIキー入力欄の`FormSection`自体を`if (ref.read(aiKeyServiceProvider).requiresUserKey) ...`で囲み、`proxy`版では**キー入力欄を出さない**(出しても保存できないため)。

**3. `AiAnalysisService`は無変更。** `aiAnalysisServiceProvider`も無変更。

**4. テスト**(受入テストは免除〈Sサイズ〉だが、以下2件は`test/ai_key_service_test.dart`に追加する)

| # | ケース | 期待 |
|---|---|---|
| 1 | `AiKeyService(AiKeyMode.ownKey)`で`saveKey('abc')`→`readKey()` | `'abc'`。`SharedPreferences.setMockInitialValues({})`を使う |

### 10.4 検証観点

- **効いたと言える判定**: `lib/`全体を`gemini_api_key`でgrepして、ヒットが`lib/services/ai_key_service.dart`の1箇所(定数定義)だけになる。
- **回帰**: personal版(`flutter run -d chrome`)で、設定画面のキー保存→統計画面のAI解釈が従来どおり動く(1回でよい)。`flutter test`全パス(`test/store_ai_fetch_test.dart`・`test/regression_section_test.dart`・`test/pca_detail_panel_test.dart`・`test/bean_create_screen_test.dart`・`test/settings_screen_test.dart`が影響範囲)。
