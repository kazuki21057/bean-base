# BeanBase Android版 コスト試算

作成日: 2026-08-07 / 対象: BeanBase 2.0 の Android 版一般公開と収益化
関連文書: [`収益化アイデア.md`](./収益化アイデア.md)

## 0. 前提と免責

| 項目 | 値 | 備考 |
|---|---|---|
| 為替 | 1 USD = 155円 | 変動する。円安が進むとAI原価は比例して増える |
| Gemini 2.5 Flash | 入力 $0.30 / 1M tok、出力 **$2.50** / 1M tok | 2026-07-02 に値上げ済み。**出力が入力の約8.3倍高い**点が本試算の要 |
| Gemini 2.5 Flash-Lite | 入力 $0.10 / 1M tok、出力 $0.40 / 1M tok | 無料枠を安く回す場合の選択肢 |
| Batch API | 通常価格の50%(2.5 Flash: $0.15 / $1.25) | 即時性が不要な機能に適用可 |
| Context Caching | キャッシュ読み出し $0.03 / 1M tok(入力の約1/10) | 固定プロンプトが長い機能で有効 |
| Play 手数料 | 15%(年間売上100万ドル以下) | 手取りは定価の85% |

**トークン数は静的解析による推定であり、実際にAPIを呼んで `usageMetadata` を取得した実測値ではない。** 特に画像入力のトークン数は不確実性が大きい(§2-2)。

## 1. トークン計測結果(2026-08-07 実施)

`lib/services/ai_analysis_service.dart` の public メソッド5個 = AI機能5個について、プロンプトの固定文字列を実測し、日本語1文字=1トークン / ASCII 4文字=1トークンで換算した。

| # | 機能(メソッド) | 呼び出し元 | 画像 | 入力トークン | 出力トークン |
|---|---|---|---|---|---|
| 1 | `extractBeanInfoFromImage` 豆情報の画像読取 | `bean_create_screen.dart:290` | **あり** | テキスト 513〜630 + **画像 258〜6,200** | 50〜150 |
| 2 | `fetchStoreInfo` 購入店情報の取得 | `store_create_screen.dart:165` | なし | 約 406 | 200〜400 |
| 3 | `interpretRegression` 重回帰の解釈 | `regression_section.dart:647` | なし | 340〜386 | 300〜450 |
| 4 | `analyzeComponents` PCA簡易解釈 | `pca_scatter_plot.dart:249` | なし | 約 232 | 100〜200 |
| 5 | `analyzeComponentsDeep` PCA深掘り解釈 | `pca_detail_panel.dart:221` | なし | 約 388 | 200〜300 |

### 1-1. 重要な発見: ログ件数に比例しない

**5機能のうち4機能は、ブリューログの総件数に依存しない。**

- PCA系2機能(#4/#5)は常に**上位2成分 × 味覚6軸固定**、要約も**常に上位/下位5件固定**しかプロンプトに含めない(`pca_scatter_plot.dart:126`、`pca_detail_panel.dart:173-186`)
- #1/#2 はブリューログではなく産地マスタ件数・フォーム入力に依存する
- 唯一 #3 の重回帰だけが、産地ダミー変数(出現5件以上の産地ごとに1列、`design_matrix.dart:100-130`)の増加に応じて緩やかに増えるが、ログ50件相当→200件相当で 115→161 トークンの差にとどまる

→ **「ユーザーがログを貯めるほど1回あたりのAI原価が膨らむ」という懸念は、この実装では成立しない。** サブスクの原価予測が立てやすい、good news。

### 1-2. 画像入力だけが桁違い

`extractBeanInfoFromImage` に渡される画像は、**リサイズも解像度制限もされていない**。

- ファイル選択: `FilePicker.platform.pickFiles(withData: true)`(`image_upload_field.dart:58-64`)— リサイズオプションなし、原寸バイト
- カメラ撮影: `ImagePicker.pickImage(imageQuality: 85)`(`image_upload_field.dart:67-70`)— `imageQuality` はJPEG圧縮率のみ。`maxWidth`/`maxHeight` **未指定のため解像度は端末カメラの原寸のまま**

スマホ写真は一般に 3000〜4000px 級。Gemini のタイル分割(概ね768×768ごとに約258トークン)を仮定すると **4×6 = 24タイル × 258 ≒ 6,200トークン**に達しうる。長辺1024pxへ縮小すれば約516トークン(2タイル)で済み、**約12分の1**になる。

## 2. AI原価(1回あたり)

Gemini 2.5 Flash、155円/USD で換算。入力1トークン = 0.0000465円、出力1トークン = 0.0003875円。

| # | 機能 | 入力 | 出力 | 入力費 | 出力費 | **合計/回** |
|---|---|---|---|---|---|---|
| 1a | 豆読取(**現状=未リサイズ**) | 6,800 | 100 | 0.316円 | 0.039円 | **0.36円** |
| 1b | 豆読取(長辺1024pxへ縮小した場合) | 1,150 | 100 | 0.053円 | 0.039円 | **0.09円** |
| 2 | 購入店情報 | 406 | 300 | 0.019円 | 0.116円 | **0.14円** |
| 3 | 重回帰解釈 | 386 | 400 | 0.018円 | 0.155円 | **0.17円** |
| 4 | PCA簡易解釈 | 232 | 150 | 0.011円 | 0.058円 | **0.07円** |
| 5 | PCA深掘り解釈 | 388 | 250 | 0.018円 | 0.097円 | **0.12円** |

**5機能の平均: 約0.17円/回(現状)、画像リサイズ後は約0.12円/回**

### 2-1. 100回あたりの原価

| ケース | 100回の原価 |
|---|---|
| 平均的な使われ方(現状) | **約17円** |
| 平均的な使われ方(画像リサイズ後) | 約12円 |
| 最悪ケース(100回すべて画像読取・未リサイズ) | **約36円** |
| 最悪ケース(画像リサイズ後) | 約9円 |

### 2-2. 前回の見立ての訂正

事前の見立てでは「手取り85円 ÷ 100回 = 1回あたり0.85円未満に収める必要があり、ギリギリ黒字」と述べたが、**計測の結果これは過大な心配だった**。実際の原価は0.07〜0.36円/回で、**月100円・100回でも粗利は約68円/月(粗利率80%)確保できる**。

理由は、**出力トークンが小さいこと**にある。全機能がプロンプト側で「2-3文で」「3項目」と出力長を明示的に制約しているため、単価の高い出力トークンが数百に収まっている。統計解析の生データをプロンプトに流し込まない設計(§1-1)も効いている。

→ **AI原価は収益化のボトルネックではない。** ボトルネックは §4 の工数と、ユーザー獲得の方である。

### 2-3. ただし2つの原価リスクがある

**(a) `maxOutputTokens` が全機能で未設定**
`GenerationConfig` で指定しているのは `responseSchema` / `responseMimeType` のみ(`ai_analysis_service.dart:201-204, 279-282`)。出力長はプロンプトの日本語指示だけで制御されており、**構造的な上限がない**。モデルが指示を無視して8,000トークン出力すると1回3.1円、100回で310円となり**一撃で赤字**になる。

→ 対策: 機能ごとに `maxOutputTokens` を設定する(#3なら600、#4なら300程度)。**コード数行で、最大の原価リスクを潰せる**。

**(b) 画像が未リサイズ(§1-2)**
現状は原価を約4倍に膨らませている。送信前に長辺1024pxへダウンスケールすれば #1 の原価が0.36円→0.09円になる。

→ この2つは**サーバを作る前に、現行コードの修正だけで実施できる**。

### 2-4. さらに下げる余地

| 施策 | 削減効果 | 備考 |
|---|---|---|
| `maxOutputTokens` 設定 | リスク遮断 | 最優先。数行 |
| 画像を長辺1024pxへ縮小 | #1 が -75% | `ImagePicker` に `maxWidth`/`maxHeight` を渡すだけ |
| Batch API(#3〜#5) | -50% | 統計解釈は即時性が低く適用しやすい。ただし非同期UIの実装が要る |
| Context Caching | 効果小 | 固定プロンプトが176〜449トークンと短く、**キャッシュの最小トークン数に届かない可能性が高い**。この規模では見送り |
| Flash-Lite への切替 | -70%程度 | 無料枠のみ Lite にする案。ただし解釈品質の低下を要検証 |

**Context Caching は当初有望と考えたが、本アプリのプロンプトは短すぎて効果が薄い。**§2-3の2施策で十分。

## 3. 金銭コスト(AI以外)

### 3-1. 初期費用(一度きり)

### 3-2. 月額固定費

| 項目 | 小規模時(MAU〜1,000) | 備考 |

### 3-3. 収益化しない場合

## 4. 開発工数(実質的な最大コスト)

| フェーズ | 内容 | 工数目安 |
|---|---|---|
| A. Android化 | `android/` 生成、Firebase依存削除、権限、署名、実機での既存機能回帰(30画面) | 3〜5人日 |
| B. ローカルDB化 | `DataService` 40メソッドの再実装、モデル移行、マイグレーション基盤、画像のローカル保存、エクスポート/インポート | 10〜15人日 |
| C. 中継サーバ | Cloud Run、匿名認証、回数カウンタ、購入トークン検証、RTDN受信 | 7〜12人日 |
| D. 課金・広告・申請 | `in_app_purchase`、`google_mobile_ads`、UMP同意、ストア素材、プライバシーポリシー、データセーフティ申告 | 7〜10人日 |
| **合計** | | **27〜42人日** |

加えて **クローズドテスト14日間(テスター12人以上)の待機期間**が公開前に必要(要件はPlay Consoleの最新表示で要確認)。

**金銭コスト(初期3,900円+月0〜500円)は些少で、真のコストは27〜42人日の工数である。** これが本試算の結論のひとつ。

## 5. 損益分岐

### 5-1. 単位経済(Pro 300円/月の場合)

| 項目 | 金額 |
|---|---|
| 定価 | 300円 |
| Play手数料 15% | -45円 |
| 手取り | 255円 |
| AI原価(100回上限、平均利用) | -17円 |
| **粗利/人月** | **約238円(粗利率79%)** |

### 5-2. 月100円/100回(初期案)の場合

| 項目 | 金額 |
|---|---|
| 手取り | 85円 |
| AI原価 | -17円 |
| **粗利/人月** | **約68円(粗利率80%)** |

**原価的にはどちらも成立する。** 粗利率はほぼ同じで、差は絶対額のみ。したがって価格を300円台にすべき理由は「原価」ではなく、**固定費の回収速度・値上げ余地・訴求力**(→[`収益化アイデア.md`](./収益化アイデア.md) §3-2)にある。

### 5-3. 固定費の回収

- 月額固定費 500円 → Pro 3人(300円プラン)または 8人(100円プラン)で回収
- 初期費用 3,900円 → Pro 17人月(300円プラン)
- **金銭的な損益分岐は極めて低い。数人の課金者で黒字化する。**

### 5-4. 工数を含めた実質評価

[`収益化アイデア.md`](./収益化アイデア.md) §8 の標準シナリオ(MAU 1,000、課金率2%)で月間手取り約6,000円 = 年72,000円。ここから AI原価とインフラ費(年間数千円)を引いて年間約65,000円。

これに対し初期工数 27〜42人日。**収益目的の投資として見ると割に合わない。** 学習価値・ポートフォリオ価値・自分が使いたいという動機を含めて判断すべき案件である。

## 6. 見落としやすいコストリスク

| # | リスク | 影響 | 対策 |
|---|---|---|---|
| 1 | **`maxOutputTokens` 未設定による出力暴走** | 1回3円超、月100回で310円 → 赤字 | 機能ごとに上限設定(§2-3a) |
| 2 | **匿名認証の無料枠悪用** | 再インストールで新しい匿名IDが取れるため、**無料枠を無限に使い回せる**。原価がユーザー数に比例せず青天井になりうる | 無料枠をGoogleアカウントログインに紐付ける / Play Integrity API で端末検証 / 無料枠を月3〜5回に絞る |
| 3 | 円安の進行 | AI原価が比例して増加 | 粗利率80%なので許容余地は大きい |
| 4 | Geminiの再値上げ | 2026-07-02に実際に値上げ済み | モデル階層化で吸収可能 |
| 5 | targetSdk 要件の年次更新 | 対応しないと**配信停止** | 毎年の保守工数を見込む |
| 6 | keystore の紛失 | **以後アップデート不能**、アプリを作り直すしかない | Play App Signing + 鍵の複数箇所バックアップ |
| 7 | ローカル保存でのデータ消失クレーム | 低評価レビュー、サポート工数 | エクスポート/インポートを無料で必ず提供 |

**#2 が金銭リスクとしては最大**。「無料枠を置くべき」という設計([`収益化アイデア.md`](./収益化アイデア.md) §3-3)と正面から衝突するため、無料枠の設計時に必ず併せて検討すること。

## 7. 結論

1. **AI原価は問題にならない。** 1回0.07〜0.36円、月100回で17円。月100円のサブスクでも粗利率80%が成立する。事前の「ギリギリ黒字」という見立ては訂正する(§2-2)。
2. **理由は出力トークンが小さいこと。** 全機能がプロンプトで出力長を制約しており、単価8.3倍の出力トークンが数百に収まっている。統計データを生でプロンプトに流し込まない設計も効いている。
3. **ログ件数に比例して原価が増える構造ではない**(§1-1)。原価予測が立てやすい。
4. **金銭コストはインフラ・運用とも実質ゼロに近い。** 初期3,900円、月0〜500円。
5. **真のコストは27〜42人日の開発工数**であり、標準シナリオの年間収益6.5万円に対して投資回収の観点では割に合わない。
6. **サーバを作る前に、現行コードで2つだけ手を打っておくべき**: `maxOutputTokens` の設定と画像の長辺1024px縮小。合わせて数時間で、最大の原価リスクと4倍の無駄を潰せる。
7. **無料枠の悪用(§6-#2)だけは設計段階で解いておくこと。** 匿名IDは再インストールで無限に取得できる。
