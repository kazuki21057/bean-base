# AIコーディングエージェント運用におけるトークン/コスト浪費対策調査レポート

- 調査日: 2026-08-15
- 調査目的: `/full_loop`開発ループ(architect/implementer/verifierへの委譲を含む日次自動開発)における「読み込み・検証の繰り返しオーバーヘッド」削減のため、Claude Code/Cursor/Devin等のAIコーディングエージェントおよびLLM反復開発ワークフロー一般で使われているトークン/コスト節約テクニックをWeb調査した。
- 調査範囲: (1)繰り返し読み込みのオーバーヘッド削減 (2)サブエージェント委譲のオーバーヘッド削減 (3)検証(テスト・ビルド)の繰り返しコスト削減 (4)その他一般的ベストプラクティス、の4観点。プロンプトキャッシング(1時間TTL)・300行超ファイルの部分読み込み・Edit/Write直後の確認Read禁止・検証コマンドの1コマンド化・応答簡潔化指示・並列化は既知採用済みのため対象外とした。

## 発見した手法一覧

### 1. Anthropic公式 Context Editing API(`clear_tool_uses_20250919`)

- 概要: Anthropic Messages APIのbeta機能。会話が閾値(デフォルト入力10万トークン)を超えると、古いtool_use/tool_resultペアをサーバー側で自動的に「[This tool result was removed by context management]」のようなプレースホルダーに置き換えて削除する。`trigger`(閾値)・`keep`(保持するtool_use数)・`clear_at_least`(最低削除量、プロンプトキャッシュ無効化とのトレードオフ調整用)・`exclude_tools`を設定可能。Token Counting APIで事前に削減効果を試算できる。
  出典: https://platform.claude.com/docs/en/build-with-claude/context-editing (取得日2026-08-15)
- 効果: Anthropic公式の複雑なリサーチタスクで平均43,588→27,297トークン(37%削減)。別事例では最大84%のツール結果削減が報告されている。
  出典: https://www.augmentcode.com/guides/ai-coding-cost-analysis-agent-token-spend (取得日2026-08-15)
- このリポジトリへの適用可能性(初見): このプロジェクトはClaude Code CLI経由で動作しており、生のMessages APIを直接呼んでいるわけではない。Claude Code CLI自体は自動コンパクション機構を持つが、`context-management-2025-06-27`ベータやclear_tool_uses設定をCLI上でユーザーが直接構成できるかは本調査では確認できなかった(**未確認**)。もし設定可能なら、サブエージェント委譲や検証コマンドの大量ツール出力(flutter analyze/test全文等)を早期に間引く効果が期待できる。

### 2. Anthropic公式 コンテキストエンジニアリングの4戦略

- 概要: (a)コンパクション=会話が上限に近づいたら要約して再初期化(アーキテクチャ上の決定・未解決バグ・実装詳細は残し、冗長なツール出力は破棄)、(b)構造化ノートテイキング=コンテキスト外の永続メモリファイルへ定期記録、(c)サブエージェントアーキテクチャ=専門化した小規模エージェントが詳細探索をこなし要約(1,000〜2,000トークン)のみ返す、(d)Just-in-Time取得=軽量な識別子(ファイルパス等)だけ保持し実行時にツール経由で読み込む。
  出典: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (取得日2026-08-15)
- このリポジトリへの適用可能性(初見): (b)は`NEXT_SESSION.md`・マスタープランで既に部分実装済み。(c)(d)は現行のarchitect/implementer/verifier委譲構成と方向性は一致するが、「委譲結果を要約1,000〜2,000トークン程度に絞る」という具体的な目安値は明文化されていない。

### 3. Anthropic公式 長時間稼働エージェント向けハーネス設計

- 概要: 初期化エージェントが機能リスト(JSON、構造化)・`init.sh`・進捗ファイルを用意し、コーディングエージェントは「一度に1機能のみ実装」という制約下で動く。新規セッション開始時は`pwd`実行→進捗ファイル読み込み→機能リスト確認→git履歴確認、という定型手順を踏むことで、状態把握のための冗長な説明・再読み込みを削減する。機能リストの強制により「過度な一括実装」「過度な完了宣言」といった無駄な再作業も防ぐ。
  出典: https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents (取得日2026-08-15)
- このリポジトリへの適用可能性(初見): `/start`→タスク選択→実装→検証→`/end`の流れ、`NEXT_SESSION.md`・改修マスタープランの構成は既にこの型に近い。「1機能=1コミット単位を厳格化し、複数タスクの並行着手を明示的に禁止する」規律の強調は、既存運用への補強として参考になる可能性がある。

### 4. サブエージェント委譲: マネージャー/ワーカーの情報非対称設計 + 参照渡し(delegation by reference)

- 概要: 階層型(マネージャー・ワーカー)委譲パターンでは「会話全体の履歴が必要なのはマネージャーだけで、ワーカーには具体的なタスク指示のみを渡す」ことでトークンを節約する。また、大きなテキストをプロンプトに埋め込む代わりに、共有ワークスペース上のファイルパスを渡し、ワーカー側がそのパスを読みに行く「参照による委譲」が有効とされる。
  出典: https://fast.io/resources/ai-agent-delegation-patterns/ (取得日2026-08-15)
- このリポジトリへの適用可能性(初見): 現状、architect/implementer/verifierへの委譲プロンプトには都度「確定済み仕様」等をテキストで書き出して渡す運用(CLAUDE.md記載)になっている。長文の仕様や調査結果がある場合は、プロンプトに全文貼るのではなく「先にファイルへ書き出し、委譲プロンプトにはそのパスだけ渡す」設計に寄せられる余地がある(ただし委譲先はファイルを自分でReadする分のツール呼び出しコストが増えるため、渡す情報量とのトレードオフを要検討)。

### 5. サブエージェント委譲: 結果をファイルシステムに書き出す運用

- 概要: サブエージェントの成果物は`.agents-output/`のようなディレクトリ配下にカテゴリ別(research/review/test等)に保存し、親セッション・ユーザー・将来のセッションから参照可能にする。`memory`フィールド(`project`スコープ推奨)を使い`.claude/agent-memory/`的な場所に記録する運用も紹介されている。
  出典: https://github.com/dianyike/claude-code-insights/blob/main/subagent-best-practices.md (取得日2026-08-15)
- このリポジトリへの適用可能性(初見): このresearcherエージェント自体が既に`docs/research/`への書き出しを義務付けられており、この設計思想に合致している。architect/implementer/verifierの成果物についても、チャット応答だけでなく該当ファイル(マスタープラン・`NEXT_SESSION.md`)への書き出しが徹底されていれば、次ループでの「文脈の渡し直し」コストを抑えられる。

### 6. サブエージェント委譲: 粒度に関するアンチパターンと単一責務原則

- 概要: 同資料は「planner→implementer→testerのような逐次委譲チェーン」をアンチパターンと明記する。各ハンドオフで判断コンテキストが失われる「電話ゲーム」効果が生じ、常時のコーディネーションオーバーヘッドを生むため。分割は「役割ごと」ではなく「コンテキスト境界に沿って」行うべきで、大量の無関係情報が入り込む場合(大容量ファイル読み込み等)に限定すべきとされる。
  出典: https://github.com/dianyike/claude-code-insights/blob/main/subagent-best-practices.md (取得日2026-08-15)
- 補足(Tembo.io、直接確認): サブエージェントは「1つの仕事」に限定し(単一責務)、ネストされたサブエージェント委譲はできない。対象が小さい編集であれば、委譲せず主会話で直接行うほうが速い、という実践的な目安も示されている。
  出典: https://www.tembo.io/blog/claude-code-subagents (取得日2026-08-15)
- このリポジトリへの適用可能性(初見): 本プロジェクトのarchitect→implementer→verifierという逐次委譲構成は、上記が名指しするアンチパターンの型そのものに近い(ただし本プロジェクトはCLAUDE.mdに確定済み仕様を明示的に書き出して渡す運用であり、単純な「口頭伝言」よりは情報忠実度の劣化を抑える設計にはなっている)。小さな修正まで毎回implementer/verifierに委譲していないか、委譲粒度を見直す余地がある可能性(**推測**、実際のログを見ないと判断できない)。

### 7. テスト影響分析(Test Impact Analysis, TIA): 変更ファイルに関連するテストのみ実行

- 概要: Gitで変更されたファイルを特定→依存関係グラフでモジュール間の影響範囲を解析→影響を受けたテストのみ実行する手法。FastAPIでの実例では全2,012テスト・88.32秒に対し、TIA適用後は750テスト・11.69秒(約8倍高速化)。「一般的な変更は比較的小さな影響範囲しか持たない」ため、開発中の反復検証(フルスイートは最終確認時のみ)に向く。Microsoft/Google/Datadog等もCIテスト時間の50〜80%削減を公表している(出典記事内の言及、一次資料未確認)。
  出典: https://www.gauge.sh/blog/how-to-make-ci-fast-and-cheap-with-test-impact-analysis (取得日2026-08-15)
- このリポジトリへの適用可能性(初見): これは「検証コマンドの1コマンド化」(既知・対象外)とは別の観点で、**検証の"範囲"を絞る**手法。Dart/Flutter向けの成熟したTIA専用ツールは本調査では見つからなかった(**未確認**、Gradle TIA・pytest-testmon等はJava/Python向け)。ただし考え方自体は転用可能で、「実装中のイテレーションでは変更ファイルに直接関係するテストファイルだけを`flutter test test/xxx_test.dart`で回し、フルスイート(`flutter test`)はverifier委譲時・コミット前の1回に限定する」運用ルールとして流用できる可能性がある。

### 8. AST/依存グラフベースのコードインデックス(構造解析+段階的深掘り)

- 概要: ベクトル埋め込みではなくAST解析でコード構造(関数・クラス・インターフェース・インポート・呼び出し関係)を抽出し、ノード=コード要素・エッジ=関係性のグラフを構築。「リポジトリ概要→特定シンボル→ソースコード」と段階的に深掘りすることで、無関係なコード全文を読まずに済ませる。40〜95%のトークン削減、SWE-benchで平均20%のトークン削減と実行時間短縮を報告(CartoGopherというツールの事例)。
  出典: https://medium.com/@jakenesler/context-compression-to-reduce-llm-costs-and-frequency-of-hitting-limits-e11d43a26589 (取得日2026-08-15、個人ブログのため参考情報扱い)
- このリポジトリへの適用可能性(初見): 既知採用済みの「Grep/Read(offset)による部分読み込み」と方向性は同じだが、専用ツール(MCPサーバー等)によるコード依存グラフの事前構築が前提であり、本プロジェクト規模(個人開発・単一Flutterアプリ)で追加ツール導入コストに見合うかは不明(**推測**、費用対効果は未検証)。

### 9. マルチモデルルーティング(高性能モデルは計画・レビューのみ)

- 概要: 実装は安価・高速なモデル、計画・レビューは高性能モデルに限定する「Aider architectパターン」で14倍のコスト削減が報告されている。
  出典: https://www.augmentcode.com/guides/ai-coding-cost-analysis-agent-token-spend (取得日2026-08-15)
- このリポジトリへの適用可能性(初見): 本プロジェクトは既に「親セッション+implementer/verifier=Sonnet、architect=Opus(⚠️上位モデルタスク・原因不明バグ等の条件時のみ)」というほぼ同型の運用を採用済み(CLAUDE.md記載)。新規性は薄いが、外部情報源による方向性の裏付けとして記録に値する。

### 10. ループ設計の効果はモデル選択より大きい/実行中のトークン予算強制

- 概要: 同じタスクでもループ設計(いつ・何を・どれだけツール呼び出しするか)次第でトークン消費が最大30倍異なり、モデル選択よりも支出への影響が大きいと報告されている。また、月次の上限だけでなく、ワークフロー実行中にトークン予算を設け、閾値到達時に「続行/縮小/承認要求/停止」を判断するランタイム制御の重要性が指摘されている。
  出典: https://www.augmentcode.com/guides/ai-coding-cost-analysis-agent-token-spend (取得日2026-08-15)
- このリポジトリへの適用可能性(初見): 「1タスクの分解粒度がコストを左右する」というユーザーの仮説を裏付ける外部情報。現行の終了条件(コスト$24超・ターン数30到達等)は"ループ全体"の上限であり、タスク実行"途中"での中間チェックポイント(例: 委譲1回ごとにコスト増分を確認し、想定超過ならタスクを打ち切って引き継ぎに回す)は明文化されていない。運用改善のアイデアとして記録するに留める(**判断は上位モデル/ユーザーに委ねる**)。

### 11. 非決定的エージェントワークフローの統計的回帰テスト削減(AgentAssay)

- 概要: LLMエージェントの出力は非決定的なため、通常の回帰テストは大量の試行を要する。Waldの逐次確率比検定(SPRT)・Wilsonスコア/Clopper-Pearson信頼区間・メタモルフィックテスト(単一出力の正誤判定でなく関係性ベースの検証)を組み合わせ、統計的に十分な確信度に達した時点で試行を打ち切ることでトークン消費を削減する手法が提案されている。
  出典: https://arxiv.org/pdf/2603.02601 (取得日2026-08-15、査読状況不明のプレプリント)
- このリポジトリへの適用可能性(初見): このプロジェクトの`flutter test`のような決定論的なユニット/ウィジェットテストには直接は適用しにくい。むしろ`AiAnalysisService`(Gemini呼び出し)のような非決定的な出力を持つ機能の回帰テストを将来設計する場合に参考になりうる、範囲外に近いが記録しておく(**推測、現状のテスト構成には未適用**)。

## 除外した手法(重複により対象外)

- プロンプトキャッシング全般(TTL活用) — 既知採用済み。ただしContext Editing API(#1)は「古いツール結果を能動的に削除する」点でプロンプトキャッシング単体とは別軸の技術のため、重複扱いにせず新規手法として記載した。
- 300行超ファイルの部分読み込み(Grep/Read offset) — 既知採用済み。#8のAST/グラフベース手法は同じ方向性の発展形だが、専用ツール導入が前提となる点で異なるため参考として記載した。
- 検証コマンドの1コマンド化(analyze→test→build) — 既知採用済み。#7のTest Impact Analysisは「検証コマンドをまとめる」のではなく「検証の対象範囲を絞る」点で別軸のため、新規手法として記載した。
- 応答の簡潔化指示、並列化 — 今回の調査では、既知の内容を上回る新規テクニックは見つからなかった。

## 変動しうる情報への注記

- Anthropic Context Editing API(#1)は現時点でbeta機能(`context-management-2025-06-27`ヘッダ必須)であり、料金体系・デフォルト閾値・Claude Code CLIでの対応状況は今後変更されうる。導入検討時は`https://platform.claude.com/docs/en/build-with-claude/context-editing`を再確認すること。
- 各種削減率(37%、84%、40〜95%、8倍、14倍等)はいずれも各出典元の特定タスク・特定計測条件下での実測値または報告値であり、本プロジェクトへの適用時に同等の効果が出る保証はない。

## 積み残し・判断が必要な点

- Claude Code CLI(本プロジェクトが実際に使っているプロダクト)がContext Editing API相当の機能をユーザー設定可能な形で内部的に持っているか/持つ予定かは未確認。公式ドキュメント(`code.claude.com/docs`)側での裏取りが必要。
- Dart/Flutterエコシステム向けの成熟したTest Impact Analysisツールの有無は本調査では確認できなかった。「変更ファイルに関連するテストのみをイテレーション中に実行する」運用ルール化は、専用ツールなしでも(変更ファイル名から対応する`*_test.dart`を人手/ルールベースで推測する形で)着手できる可能性があるが、この設計判断自体は範囲外(上位モデル/ユーザーの判断が必要)。
- サブエージェント委譲粒度(#6)が本プロジェクトの実運用で過剰かどうかは、実際の`.claude/loop_state.md`等のログ分析が必要であり本調査の範囲外。
- #4(参照渡し)・#10(実行中のトークン予算強制)は具体的な運用ルールへの落とし込み方が複数考えられるため、採否・設計は本プロジェクトの意思決定者(architect/ユーザー)に委ねる。
