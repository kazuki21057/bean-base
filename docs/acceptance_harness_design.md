**本書の位置づけ**: 「検証を物語(verifierの報告文)ではなく契約(再実行可能な機械判定)にする」ための規約の正本。実装は後続タスク(§9)で行う。

## 1. 目的と非目的

### 目的

現在の検証は2層に分かれている。

| 層 | 実体 | 性質 |
|---|---|---|
| 機械判定 | `tools/verify.ps1`の8項目(analyze/test/build等) | 再実行可能・タスク非依存 |
| ナラティブ | verifierのブラウザ目視+日本語報告文 | 再実行不可・タスク依存・人間の読解が必要 |

問題は**「そのタスクの完了条件を満たしたか」という最も重要な判定が、まるごと下の層(ナラティブ)にある**こと。`tools/verify.ps1`が全green でも、それは「壊れていない」ことしか言っておらず「作ったものが仕様どおり動く」は誰も機械的に確かめていない。本設計はこの**タスク固有の完了条件**を、exit code とJSONで表現される**受け入れ資産(acceptance asset)**として残し、以後のループで自動的に回帰実行されるようにする(ゴールデンループ化)。

### 非目的(やらないこと)

- **新しいテストランナーを作らない。** Dart側は既存の`flutter_test`をそのまま使い、`test/acceptance/`という置き場所と命名に「受け入れ基準」という意味づけを与えるだけにする(§5)。
- **全タスクへの一律義務化をしない。** 適用範囲は§2で明確に絞る。
- **verifierの目視確認を廃止しない。** 機械判定できない領域(配色・字形・実サービス疎通)は引き続きverifierが担い、受け入れ資産と併用する(§6)。
- **本番Sheets/Drive/GASへ受け入れスクリプトから直接アクセスしない**(`rules/verification.md`§既知の失敗しやすい検証経路の「GASエンドポイントへの直接curl禁止」、教訓L114・L47と整合)。

## 2. 適用範囲の判定基準(**本設計の中核**)

### 2.1 必須化の条件

以下の**3条件をすべて満たす**タスクのみ、受け入れ資産の作成を必須とする。

| # | 条件 | 判定の仕方 |
|---|---|---|
| A | マスタープランの**サイズがMまたはL** | タスク表のサイズ列 |
| B | **実行される成果物**を変更する。すなわち`lib/`配下の`.dart`、`tools/`配下の`.ps1`/`.sh`/`.dart`/`.js`、`.claude/hooks/`配下の`.js`、`gas/`配下の`.gs`のいずれかを変更する | 実装完了後の`git diff --name-only` |
| C | 完了条件が**値・状態・存在有無**で表現できる(数値が一致する/文言が表示される/ファイルが存在する/フックが検知してログ行が出る、等) | タスク行の完了条件を読む |

### 2.2 免除(受け入れ資産を作らなくてよい)

上記のいずれかを満たさない場合は免除。特に以下は**明示的に対象外**とする。

| 免除カテゴリ | 例 | 理由 |
|---|---|---|
| **ドキュメント・ルールのみの変更** | T5-A49〜A56、`docs/`・`rules/`・`NEXT_SESSION.md`・`CLAUDE.md`・`SKILL.md`・`.claude/agents/*.md`のみの編集 | 条件Bを満たさない。「文書に一文が入ったか」は`grep`1回で足り、スクリプト化はオーバーヘッドが完全に上回る |
| **サイズS** | T5-A55(ルール明文化)、文言の追記・誤字修正 | 条件Aを満たさない。受け入れ資産の作成コスト(実装+デバッグで数十行)がタスク本体を上回る |
| **設計のみのタスク**(⚠️上位モデルで実施) | T5-A57〜A59、本タスク | 成果物が設計書のみでコードが無い。条件B・Cとも満たさない |
| **視覚的主観判断だけが完了条件のタスク** | 「配色を落ち着いた色味にする」「余白を詰めて見やすくする」 | 条件Cを満たさない。goldenで固定できるのは「意図せず変わっていないこと」だけで、「良くなったか」は機械判定できない(§5.3) |

**境界事例の裁定(迷ったときの既定)**:

- 「Mサイズだが変更が`docs/`と`tools/`にまたがる」→ `tools/`側の変更が実行時の振る舞いを変えるなら**必須**(条件B該当)。`tools/`のコメント修正だけなら免除。
- 「Lサイズだが完了条件が『設計方針が確定している』」→ 免除(条件C不該当)。
- 「Sサイズだがバグ修正で再発防止が要る」→ **原則免除だが、同じ症状の2度目以降の修正なら必須に格上げする**(教訓L112「同じ症状の2度目の修正依頼は前回が症状の一部しか直していない疑いを持つ」)。この格上げは親が判断する。
- 「外部サービス依存で完全な機械判定ができない」→ **免除しない。§6の3層モデルに従い、機械判定できる層(L1)だけでも受け入れ資産にする。**

### 2.3 判定と記録(免除の言い逃れを塞ぐ)

適用判定は**タスク選定直後に親(オーケストレーター)が行い、結果を必ず記録する**。記録しないと「面倒だから作らなかった」が事後的に見分けられなくなる。

記録先は`docs/改修マスタープラン.md`のタスク行の**完了条件セルの末尾**。以下の2形式のみを認める(列は増やさない。`grep -n "受入:" docs/改修マスタープラン.md`で一覧できる)。

```
／受入: test/acceptance/t5_a61_acceptance_test.dart
／受入: tools/acceptance/t5_a50_check.ps1
／受入: 免除(ドキュメントのみ)
／受入: 免除(Sサイズ)
／受入: 免除(設計タスク)
／受入: 免除(視覚判断のみ)
```

免除理由は上記4つの固定文言から選ぶ(自由記述を認めない。認めると「今回は特殊なので免除」が積み上がる)。4つのどれにも当てはまらないのに免除したい場合は、免除せず§6のL1だけでも作る。

## 3. 受け入れ資産の規約

### 3.1 2種類と使い分け

| 種別 | 配置・命名 | 使う場面 |
|---|---|---|
| **Dart受け入れテスト**(既定) | `test/acceptance/<id>_acceptance_test.dart` | `lib/`配下の変更。ロジック・UI・モデル・サービスすべて |
| **PowerShell受け入れスクリプト**(例外) | `tools/acceptance/<id>_check.ps1` | 検証対象がDartでないもの——`tools/`のスクリプト、`.claude/hooks/`のフック、`gas/`の列定義とDart側マッピングの突合、ファイルのエンコーディング/BOM、生成物の存在 |

**既定はDart側**。`.ps1`はDartのテスト枠で表現できない場合にのみ選ぶ(理由: `.ps1`はWindows専用で、非Windows環境のループでは実行できない——教訓L133)。

**`<id>`の正規化規則**: タスクIDを小文字化し`-`を`_`に置換する。`T5-A50` → `t5_a50`、`T5-B12` → `t5_b12`。

### 3.2 Dart受け入れテストの規約

- 通常の`flutter_test`ファイル。`flutter test`(=`tools/verify.ps1`の`test`項目)が自動的に拾うので、**新しい実行系は不要**。
- ファイル冒頭に、そのタスクの完了条件を**マスタープランの文言そのまま**でコメントとして書く。これが「契約書の本文」に相当する。

  ```dart
  /// 受け入れテスト: T5-A61
  /// 完了条件(docs/改修マスタープラン.md より): <完了条件セルの文言をそのまま>
  ```

- `group('受け入れ(T5-A61)', () { ... })`で括る。**group名にこの形式でタスクIDを含めること**(§7の存在判定がこの文字列を探すため)。
- 1タスクにつき1ファイルを既定とするが、**既存のテストファイルに書いたほうが自然な場合は新規ファイルを作らず既存ファイルに上記group名で追加してよい**(例: `test/log_edit_screen_test.dart`に`group('受け入れ(T5-A61)', ...)`を足す)。その場合はマスタープランの`／受入:`にそのファイルパスを書く。
- 本番サービスへ通信しない。`test/helpers/fake_master_notifiers.dart`等の既存fakeを使う(既存テストの慣例に従う)。

### 3.3 PowerShell受け入れスクリプトの規約

**配置**: `tools/acceptance/<id>_check.ps1`(このディレクトリは新設)

**必須の書式**:

- 先頭に`#requires -Version 5.1`。
- **BOM付きUTF-8で保存する**(日本語コメントを含む`.ps1`をBOM無しで保存するとPowerShell 5.1が構文エラーになる——教訓L127・L142)。
- 進捗・診断メッセージは**すべてstderrへ**出す(`[Console]::Error.WriteLine("[acceptance] ...")`)。stdoutにはJSON以外を一切書かない(`tools/verify.ps1`と同じ思想)。
- **stdoutの最終行に、下記スキーマのJSONを1行(改行なし)で出力する。**
- 読み取り専用。本番Sheets/Drive/GASへアクセスしない。リポジトリのファイルを書き換えない(一時ファイルが要る場合は`$env:TEMP`配下)。
- 冪等。何度実行しても同じ結果を返す。

**exit code規約**:

| exit code | 意味 | verify.ps1側の扱い |
|---|---|---|
| `0` | **合格**。受け入れ基準をすべて満たした | pass |
| `1` | **不合格**。基準を満たさない項目があった | **fail**(トップレベル`ok:false`) |
| `2` | **判定不能(前提不足)**。判定に必要な環境・ファイルが無い(例: Android SDK未整備、対象が未実装) | **skip**(failにしない。`note`に理由を出す) |
| `3`以上・その他 | **スクリプト自身の異常**(例外・引数不正) | **fail**(スクリプトのバグとして扱い、修正対象) |

`0`/`1`/`2`以外を「合格」と解釈してはならない。`2`(skip)と`1`(fail)を混同しないこと——「未実施」を「合格」として飲み込むのは、この仕組みが最も避けたい失敗モードである(教訓L118)。

**stdout JSONスキーマ(1行)**:

```json
{"task":"T5-A50","ok":true,"skipped":false,"reason":"","checks":[{"name":"BOM破壊を検知する","ok":true,"detail":"hook exit=1, log行あり"},{"name":"正常ファイルは通す","ok":true,"detail":"hook exit=0"}]}
```

| キー | 型 | 内容 |
|---|---|---|
| `task` | string | タスクID(`T5-A50`形式、正規化前) |
| `ok` | bool | 全チェック合格なら`true`。exit codeと必ず一致させる(`ok:true`⇔exit 0) |
| `skipped` | bool | exit 2 のとき`true` |
| `reason` | string | `ok:false`または`skipped:true`のときの1行理由(日本語) |
| `checks` | array | 個別チェックの配列。`name`(日本語の判定名)・`ok`・`detail`(観測値を1行で) |

`detail`には**観測した実値**を書く(「OK」ではなく「exit=1, 検知ログ2行」)。これが「物語ではなく証拠」の実体になる。

**テンプレート**(実装時にこの構造をそのまま使う。実処理は`$checks`への追加のみ):

```
1. #requires + BOM付きUTF-8 + [Console]::OutputEncoding をUTF8に固定
2. $ErrorActionPreference = "Continue"、全体を try/catch で囲む
3. リポジトリルートへ Set-Location(git rev-parse --show-toplevel、tools/verify.ps1 と同じ手順)
4. 前提チェック → 足りなければ JSON(skipped:true) を出して exit 2
5. 個別チェックを実行し $checks に積む
6. JSON を1行で Write-Output し、$ok なら exit 0、でなければ exit 1
7. catch: JSON(ok:false, reason:"例外: ...") を出して exit 3
```

## 4. 「契約」に書いてよい判定条件の型

受け入れ資産に書く判定は、以下の型に還元できるものに限る。これ以外(「使いやすくなった」「自然な見た目」)は契約にしない。

| 型 | 例 | 実装手段 |
|---|---|---|
| 値の一致 | 残豆量が`120.0`になる、PC1寄与率が`0.42±0.01` | `expect(actual, closeTo(...))` |
| 状態遷移 | 保存ボタン押下後に一覧へ戻り、対象行が1件増える | widgetテスト |
| 文言の存在 | エラー時に`豆の在庫が不足しています`が表示される | `find.text(...)` |
| 不在 | 旧ラベル`Bean Stock`が画面に残っていない | `findsNothing` |
| レイアウト健全性 | 3端末幅でoverflowが出ない | `test/helpers/overflow_test_helper.dart` |
| 見た目の非退行 | 共通部品の描画が変わっていない | `test/golden/` |
| ファイル・生成物の存在/内容 | フックが登録されている、BOMが保持されている | `.ps1`受け入れスクリプト |
| ログ行の出現 | `[Antigravity] ...`の特定行が出る | widgetテスト or `.ps1` or ブラウザコンソール(§6のL2) |

## 5. 既存テスト資産との関係(車輪の再発明をしない)

### 5.1 `test/`配下の既存テスト(68ファイル)

**役割は変えない**。これらは「壊していないこと」を見る回帰網であり、受け入れ資産は「作ったものが仕様どおりであること」を見る。**同じ`flutter test`が両方を実行する**ため、実行系・CI・`tools/verify.ps1`の`test`項目に変更は不要。違いは置き場所(`test/acceptance/`)とgroup名(`受け入れ(<ID>)`)という**トレーサビリティのための規約だけ**である。

したがって「受け入れテストを書く」は、実務上は**「そのタスクの完了条件をそのまま1つのgroupに書き下ろし、タスクIDで引けるようにする」**という作業に等しい。新規の学習コストはほぼ無い。

### 5.2 `test/helpers/overflow_test_helper.dart`

UI画面を追加・改変するタスクの受け入れ資産では、**`pumpAndDetectOverflow` + `expectNoOverflow`を必ず1ケース含める**(3サイズ: 360x690 / 411x914 / 320x690)。これでレイアウト崩れの受け入れ判定がエミュレータ不要・機械判定で済む。`SharedPreferences.setMockInitialValues({})`とネットワーク依存プロバイダのfake差し替えが必要な点は`test/settings_screen_overflow_test.dart`の先例に従う(`rules/verification.md` 6項)。

### 5.3 `test/golden/`

**位置づけ**: 「意図せず見た目が変わっていないこと」の受け入れ基準。**「デザインが良くなったこと」の判定には使えない**(§2.2の視覚的主観判断が免除である理由)。

- 共通部品(`lib/widgets/`)を新規追加するタスクでは、受け入れ資産としてgoldenを1件追加する(ライト/ダーク2バリアント、`test/golden/golden_test_helper.dart`に従う)。
- **既存goldenの`--update-goldens`はエージェント判断では禁止**(`rules/verification.md` 5項)。この禁止は受け入れハーネス導入後も一切緩めない。受け入れテストを通すためにgoldenを更新する、は最も危険な抜け道になるため、**受け入れ資産の実装時にgoldenの更新が必要になったら、implementerは更新せず親へエスカレーションする**。

### 5.4 `integration_test/`(未整備、T5-A7)

現時点で存在せず実行環境(エミュレータ)も未整備のため、**受け入れ資産の置き場所として使わない**。T5-A7完了後にE2E層の受け入れをここへ載せるかは、その時点で再検討する(本設計では規約を作らない)。

## 6. 外部サービス依存タスクの扱い(3層モデル)

GAS/Sheets/Drive/Gemini が絡むタスクは完全な機械判定ができない。**「できないから何もしない」ではなく、層に分けて機械判定できるところまで機械判定する**。

| 層 | 何を判定するか | 手段 | 誰が実行するか |
|---|---|---|---|
| **L1(機械判定・必須)** | 外部サービスと**接する自コード**の正しさ。`fromJson`の`.toString()`化、`SheetsService`のkeyMapに期待する日本語列名が入っているか、モデル追加時の書き込み側マッピング2箇所+GAS列プロビジョニングの3点が揃っているか(教訓L16・L42・L90)、リクエスト組み立ての形 | Dart受け入れテスト(fakeレスポンス)+ 必要なら`.ps1`で`gas/Code.gs`と`lib/services/sheets_service.dart`の列名突合 | `flutter test` / verify.ps1 |
| **L2(半機械判定)** | 実サービスと**疎通して期待どおりの結果になる**こと。ただし判定は目視の印象ではなく**文字列一致**で行う | verifierが`build/web`をローカル配信し、アプリUIを操作して`read_console_messages(pattern指定)`で**あらかじめ決めた正規表現に一致する`[Antigravity]`ログ行**を取得。報告には**観測した行そのものを引用**させる | verifier(手動) |
| **L3(目視のみ)** | 配色・字形・アニメーション・実画像の見え方 | スクリーンショット1〜2枚 + 確認観点の明示 | verifier(手動) |

**規約**:

- L1は**必須**。外部依存タスクでも受け入れ資産を免除しない。
- L2は、タスクの受け入れ基準として**期待するログ行の正規表現を親が事前に確定させ、委譲プロンプトに書く**(例: `\[Antigravity\] Sheets: 豆マスタ更新 成功 id=`)。決めていない正規表現をverifierに考えさせない。ログ行が無いなら、そのタスクの実装で`debugPrint('[Antigravity] ...')`を1行足すところまでを実装タスクに含める。
- L3はゲート判定に使うが、受け入れ資産には**しない**。
- **受け入れスクリプトからGASへ直接HTTPを投げることを禁止**する(サンドボックスの疎通が回によって変動しL47、直接curlは`doPost`にボディが届かないL114。「たまに落ちる受け入れスクリプト」は仕組み全体の信頼を壊す)。

### 7.2 `Invoke-CheckAcceptance` の仕様(実装判断を残さない粒度)

**入力**: `$Task`(空文字なら「タスク指定なし」)、`tools/acceptance/*.ps1`、`test/acceptance/`。

**処理**:

1. `tools/acceptance/`配下の`*_check.ps1`を**全件**実行する(ゴールデンループ=過去タスクの受け入れも毎回回帰実行する)。
   - 実行: `Invoke-LoggedCommand -FilePath "powershell" -ArgumentList @("-NoProfile","-ExecutionPolicy","Bypass","-File",<相対パス>) -LogPath <acceptanceログ> -TimeoutMs 60000`。
   - **ログは1スクリプトにつき1ファイル**(`Get-LogPath "acceptance_<id>"`)。
   - stdout/stderrがマージされたログから、**先頭が`{`である最終行**をJSONとして`ConvertFrom-Json`する。パースできなければ`ok=false`, `reason="json_parse_failed"`。
   - exit code の解釈は§3.3の表に従う。タイムアウトは`ok=false`, `reason="timeout"`。
2. `$Task`が指定されている場合、**そのタスクの受け入れ資産が存在するか**を判定する。存在すると認めるのは以下のいずれか。
   - `tools/acceptance/<id>_check.ps1` が存在する。
   - `test/acceptance/<id>_acceptance_test.dart` が存在する。
   - `test/`配下のいずれかの`.dart`に文字列 `受け入れ(<タスクID>)` が含まれる(既存ファイルへのgroup追加を許すため。§3.2)。
   - **どれも無ければ** `ok=false`, `reason="acceptance_missing"`。これが「必須なのに書かなかった」を機械的に捕まえる唯一の仕掛けである。
3. `$Task`が指定され、かつ`test/acceptance/<id>_acceptance_test.dart`が存在する場合、そのファイルだけを`flutter test <path>`で**もう一度単独実行**し、当該タスクの合否を独立に記録する(`TimeoutMs = 300000`)。
   - 理由: `test`項目は全件まとめての合否しか返さないため、「このタスクの契約が通ったか」を単独で言えない。1ファイルの再実行コスト(数十秒)は`-Task`指定時のみ発生し、M/L規模タスクでは十分に見合う。
   - 既存ファイルへのgroup追加形式(2の3番目)の場合は再実行せず、`dart.note`に`"既存テストファイル内のgroupのため単独再実行は省略(testの結果に含まれる)"`と記録する。
4. `$Task`が空で`tools/acceptance/`も空(またはディレクトリ無し)の場合は `ok=true, skipped=true, note="受け入れ資産なし(タスク指定なし)"`。

**出力(JSON)**:

```json
"acceptance": {
  "ok": true,
  "task": "T5-A61",
  "required": true,
  "dart": {"found": true, "path": "test/acceptance/t5_a61_acceptance_test.dart", "ok": true, "note": ""},
  "scripts": [
    {"name": "t5_a50_check.ps1", "exit": 0, "ok": true, "skipped": false, "summary": "2/2 pass"}
  ],
  "passed": 3, "failed": 0, "skipped": 0
}
```

失敗時は上記に加え `"reason": "<acceptance_missing|script_failed|script_error|json_parse_failed|timeout>"` と、失敗した項目の`log`パスを含める(成功項目のlogパスは出さない——読ませないため)。

### 7.3 `tools/verify.sh`(Bash版)

同一のキー・同一の意味で`check_acceptance`を実装する。ただし:

- `.ps1`の実行は`pwsh`がPATHにある場合のみ。無い場合は各スクリプトを`{"name":...,"skipped":true,"reason":"pwsh_not_found"}`として**skip扱い**(failにしない)。
- Dart側(`test/acceptance/`)の判定はOSに依存しないので同一に動く。
- これにより非Windows環境のループでも`acceptance`項目が理不尽に落ちない(教訓L133)。
