## 0. 前提(ユーザー確定事項、2026-08-07)

| 論点 | 決定 |
|---|---|
| 収益化範囲 | **v1.0 から AI サブスクまで一気に**(中継サーバ+アカウント+回数カウンタ+Play課金検証+RTDN を初回リリースに含む) |
| UI 方針 | **全画面を一から新規デザイン**(デザイントークン/コンポーネント体系から作り直す) |
| 自動実行基盤 | **Windows タスクスケジューラ**(常時ON の PC でヘッドレス `claude -p` を定期実行) |
| 無人実行の権限 | **main へ自動 push**。ただし検証エージェントの性能向上が前提。トークン増は許容 |
| 対象 OS | **Android のみ**(iOS は対象外) |
| 開発環境 | 主に Windows(常時ON)、たまに Ubuntu。ユーザーはスマホからアクセスすることが多い |

### 0-1. 明示した懸念(方針は変えない)

収益化アイデア §7 は「Phase 1 で実際の AI 利用頻度を観測してから価格と回数を決める」段階戦略を推奨している。v1.0 から AI サブスクを載せると、**価格・無料枠回数の根拠が推測ベースになる**。加えてクローズドテスト14日間の待機がリリース日を後ろへ押す。

ユーザーが全部入りを選択済みのため計画は全部入りで進めるが、**緩和策として、価格と無料枠回数はサーバ側の設定値として持ち、アプリに埋め込まない**。公開後に実利用データを見て、アプリを再申請せずに調整できる形にする(→ Phase 5-P4 の完了条件に含める)。

## 1. 全体像 — 3トラックを並走させる

```
トラック A: 開発運用基盤   ← 最初に完成させる。以降の全作業の生産性を決める
トラック B: 製品開発       ← P0〜P4。夜間ループが主に回す
トラック C: リリース準備   ← 人手が要る。早く着手するほど待ち時間を吸収できる
```

### 1-1. なぜ A が先か

コスト試算 §4 の見積り(27〜42人日)に、今回追加された「全画面の新規デザイン」と「v1.0 から AI サブスク」を足すと **実質 40〜60人日規模**になる。Pro プランのトークン上限のもとで日中の有人セッションだけを積み上げてこれを消化するのは非現実的。

**夜間の自動実行が動いて初めてこの規模が成立する。** したがってトラック A は「あったら便利な改善」ではなく**前提条件**であり、B より先に完成させる。

### 1-2. なぜ C を早く始めるか

Google Play の個人デベロッパーアカウントには **クローズドテスト(テスター12人以上 × 14日間連続)** の要件がある。これは製品版申請の**直前**ではなく**手前**に必要な待機時間で、しかも「人を12人集める」という開発と無関係な律速がある。

**テスター確保と Play Console 登録は、開発の進捗と無関係に今日から始められる。** ここを後回しにすると、コードが完成しても2週間+人集めの期間だけリリースが遅れる。これが本計画のクリティカルパス。

### 1-3. 依存関係(概略)

```
トラックA ─────────────────────────────────────────▶ (以降すべての前提)
   │
   ├─ P0 エディション足場 ─┬─ P1 ローカルDB ─┬─ P4 収益化基盤 ─┐
   │                       │                  │                  │
   │                       └─ P2 UI新規設計 ──┴─ P3 インサイト ──┤
   │                                                              │
トラックC(並行、人手)───────────────────────────────────────┴─▶ リリース
```

- P2(UI)は P1(ローカルDB)の完了を待たない。`DataService` 抽象があるため、UI は Sheets のまま開発できる
- P3(インサイト)は P2 のコンポーネント体系が固まってから
- P4(収益化)は P1・P2 が終わってから。広告枠と課金導線が UI に食い込むため

## 2. トラック A: 開発運用基盤

**詳細は [`開発運用基盤設計.md`](./開発運用基盤設計.md)(自動実行)と [`検証強化設計.md`](./検証強化設計.md)(検証体制)。** 本節は要点のみ。

### 2-1. 夜間自動実行

Windows タスクスケジューラ → `tools/night_loop.ps1` → `claude -p "/night_loop"` の3段構成。

**5時間枠の遵守が本計画の要**。ラッパースクリプトが `~/.claude/projects/` 配下の transcript 更新時刻を見て、**5時間以内に人間のセッションがあれば発火をスキップ**する。これによりユーザーの日中利用と夜間ループが同じ枠を食い合わない。加えて週次の実行回数上限を持たせる。

発火は **23:00 / 04:10 / 09:20**(5時間10分間隔、09:20 は設定で無効化可)。

### 2-2. 検証体制の再編(main への自動 push の前提)

`rules/lessons_archive.md` の115件の教訓を「検証をすり抜けた欠陥」の観点で読み直すと、**逸出は8パターンに集約され、その全部が `flutter analyze` / `flutter test` が緑でも通過する**。ここに手を打たない限り自動 push は危険、というのが調査結論。

対策は3層。

| 層 | 内容 | 狙う逸出パターン |
|---|---|---|
| 層1 | **決定論的な検証をスクリプトへ降ろす**(`tools/verify.ps1` が JSON 1つを返す) | release ビルド限定バグ、`.g.dart` 再生成漏れ |
| 層2 | **自動回帰スイート**(エミュレータ `integration_test` + golden テスト) | 視覚回帰、起動・保存経路の破壊 |
| 層3 | **敵対的レビュー**(`adversary` エージェント) | 契約ズレ、サイレント fallback、横展開漏れ、部分英語、再修正の不徹底 |

エージェントは `verifier` 1体 → **`verifier` / `ui_verifier` / `adversary` の3体**へ。加えてユーザー提案の **`researcher`**(情報収集)を新設。

**トークンは増えない見込み**: 層1 により `analyze`/`test`/`build` の生出力(毎回7k〜13k文字、以降の全リクエストに課金され続ける)が JSON 1つに置き換わるため。実測して `docs/token_optimization_design.md` §7 に記録する。

### 2-3. main への自動 push ゲート

**4条件すべてを満たしたときだけ main へ自動 push。**

1. `tools/verify.ps1` が全項目 green
2. `integration_test` スモークが全パス
3. `ui_verifier` が異常なしと報告(UI 変更があった場合のみ判定対象)
4. `adversary` の Critical 指摘がゼロ

1つでも欠けたら `night/<タスクID>` ブランチへ push + PR 作成 + `PushNotification` で通知し、main には触れない。**クリーンなら完全自動、怪しいときだけ人間に上がる。**

## 3. トラック B: 製品開発

### P0. エディション足場 + 原価リスクの遮断

`../android_monetization/コードベース構成方針.md` §7 の E-1〜E-4 をそのまま実施する。**E-1「差分ゼロの2エントリポイント」を先に作る**のが要点で、足場だけ通しておけば以降の Android 化タスクが既存動作を壊さずに積める。

**先行して即やる(エディション非依存、数時間)**:

- **`maxOutputTokens` の設定** — 全 AI 機能で未設定。出力長がプロンプトの日本語指示だけで制御されており、暴走すると1回3円超・月100回で310円の赤字になりうる(コスト試算 §2-3a)。**最大の原価リスクを数行で潰せる**
- **画像の長辺1024pxへの縮小** — 現状は原寸のスマホ写真を送っており原価が約4倍(同 §2-3b)

### P1. ローカル DB 化

公開版のデータは端末ローカルに保存する(Sheets は作者個人のものなので公開版では使えない)。

- **パッケージ選定は `researcher` が調査**。`drift` を第一候補とする(型安全なマイグレーション基盤を標準で持ち、逸出パターン#1「契約ズレが静かに null になる」に最も効く)
- `DataService`(`lib/services/data_service.dart`)の実装として `LocalDbService` を追加し、`dataServiceProvider` を `AppEdition.useLocalDb` で分岐(E-3 で作る接続点をそのまま使う)
- **マイグレーション基盤は最初のコミットで入れる。** 「統計処理は順次アップデート」という要件がある以上スキーマ変更は毎回発生する。後付けは必ず破綻する
- 画像のローカル保存(`path_provider`。既に依存にある)
- **エクスポート/インポート(JSON/CSV)は無料機能として必ず入れる** — 機種変更・アンインストールでのデータ全消失はレビュー低評価とサポート工数の最大の発生源(コスト試算 §6-#7)

**副次的な利点**: ローカル DB 実装は「選べるバックエンド」として personal 版(web)からも使えるため、Sheets 障害時の退避手段になる。

### P2. UI 全画面の新規デザイン

**順序が重要**: トークン → コンポーネント → 画面 の順に固める(L10「UIモックを複数画面まとめて作る際は共通部品を先に作る」)。

1. **デザイントークン** — 色・タイポ・余白・角丸・エレベーション + **ダークモード**。既存の `mainColorProvider`(設定画面のメインカラー)との関係を先に決める
2. **共通コンポーネント** — カード / リスト行 / 空状態 / ローディング / エラー / ボトムシート / 数値入力。**各コンポーネントの golden を同時に撮る**
3. **主要4系統** — ホーム / 記録(抽出→評価) / インサイト / オンボーディング
4. **残りの画面**(マスタ管理など)を新体系へ移植

**モバイル固有の作り込み**(現行 web 版に無い):

- タップ領域48dp、スワイプ操作、ハプティクス
- **抽出タイマーのバックグラウンド動作と通知** — 「淹れながらスマホを見ない」という実利用に必須。web 版に無い最大の価値差
- 画面回転、ダークモード、戻るジェスチャ、端末フォントサイズ設定への追従

**注意**: 既存の23画面のうち `lib/screens/debug/` と `lib/screens/mock/` は personal 専用。`enabledScreens` のホワイトリストから外し、公開版のデザイン対象に含めない。

### P3. 統計の「洗練された情報のみ」化

**方針: 公開版では生の統計量(PCA 負荷量・回帰係数・p値・寄与率・固有値)を画面に出さない。** 代わりに「**所見1文 + 根拠1つ + 次の一手**」に変換したインサイトカードだけを出す。

- **データ不足時は統計を出さず「あと◯件でインサイトが使えます」の進捗表示** — 収益化アイデア §9-2 が指摘する「新規ユーザーは価値を感じる前に離脱する」構造への直接対策。PCA・回帰・GP はログが数十件貯まらないと意味のある出力を出せないため、そこまでの動機づけを UI が担う
- **不確実性は数値ではなく確信度3段階 + 視覚的な幅**で表現する
- **少数データでも出せる簡易フィードバック**(前回との比較など)を無料で提供し、インストール直後から価値を出す

> ⚠️ **設計上の衝突と、その解き方**: `statistics_feature_design.md` §0 の絶対規則は「統計量は点推定+不確実性をセット表示」を要求しており、この表示方針と表面的に衝突する。**勝手に破らない。** 設計書に「公開版の表示規則」の節を追加する形で整合を取る(不確実性を**捨てる**のではなく、数値からビジュアルへ**表現を変える**だけ、と位置づける)。これは設計判断なので architect が有人セッションで行う(T5-B30)。

### P4. 収益化基盤(v1.0 に含む)

収益化アイデア §1 のとおり、**AI に送る内容と課金状態だけはサーバを経由**する。ブリューログ・マスタデータは端末ローカルで完結する。この線引きをプライバシーポリシーに明記する。

| 要素 | 内容 | 根拠 |
|---|---|---|
| 中継サーバ | Cloud Run。`アプリ → 中継サーバ → Gemini`。**APK に Gemini キーを埋めない**(逆コンパイルで抽出される) | 収益化アイデア §1 |
| アカウント | **Google アカウントログインを必須**。匿名認証だけでは再インストールで無料枠を無限に取り直せる(**金銭リスク最大**) | コスト試算 §6-#2 |
| 回数カウンタ | サーバ側。端末側カウンタは改ざん可能 | 収益化アイデア §1 |
| 課金 | `in_app_purchase` + **購入トークンの Google Play Developer API によるサーバ検証** + RTDN 受信 | 収益化アイデア §1 |
| 広告 | `google_mobile_ads` + UMP 同意。**バナー(一覧下部)+ リワード広告で AI 1回付与**。インタースティシャルは記録アプリの UX を壊すので入れない | 収益化アイデア §2 |
| Pro の中身 | AI 月100回 / 広告非表示 / クラウドバックアップ / エクスポート の**束ね売り**。300〜480円/月 | 収益化アイデア §3-2 A案 |
| 無料枠 | AI 月3〜5回。**必ず置く**(使ってみないと価値が分からない機能のため)が、悪用対策とセット | 収益化アイデア §3-3 |
| 価格・回数の持ち方 | **サーバ側の設定値**。アプリに埋め込まない | 本書 §0-1 |

**インフラ固定費は月0〜500円**(Cloud Run は scale-to-zero + 無料枠内、Firestore/Auth も無料枠内)。数人の課金者で回収できる(コスト試算 §3-2、§5-3)。

## 5. 夜間ループを成立させる最重要ルール: 設計の先出し

**夜間ループには設計判断を一切させない。**

理由は2つ。

1. **Pro プランで上位モデル(Opus 系)のサブエージェントが使えるか不確実**(T5-A14 で実測する)
2. **設計判断を含むタスクは失敗率が高く、無人で main に push させるにはリスクが高い**

したがって運用は次の形になる。

| | 有人セッション(週1〜2回) | 夜間ループ(自動、1日2〜3回) |
|---|---|---|
| やること | architect が設計書を書き、タスク表へ分解する。デプロイ・ストア提出・本番データ操作 | 確定済みタスクを1件ずつ消化 |
| 粒度 | implementer が迷わない粒度まで確定(フィールド名・テーブル/列名・画面ID・引数表・文言・境界値・既知の地雷) | 設計判断が必要と判明した時点で**手を止めて通知**し、次の有人セッションへ回す |

**この「設計の在庫」を切らさないことが夜間ループの稼働率を決める。** 在庫が尽きると夜間ループは何もせず終わるだけになる。有人セッションでは常に「次の2〜3週間ぶんの確定タスク」を作っておく。

## 6. 進め方のまとめ(実行順)

1. **トラック A を完成させる**(T5-A1〜A14)。有人監視下で `night_loop.ps1` を1回試走してからタスクスケジューラに登録する。**いきなり無人で回さない**
2. 同時に **トラック C の 4-1 を開始**(Play Console 登録・テスター募集)
3. **P0** を夜間ループで消化(設計済みなので即着手可)
4. 有人セッションで **P1・P2 の設計書**を先出し → 夜間ループが実装
5. **P3・P4** も同様に「設計先出し → 夜間実装」
6. トラック C の素材・申告を揃え、内部テスト → クローズドテスト → 製品版

## 7. 未決事項(着手前に決める)

| # | 論点 | 判断の目安 |
|---|---|---|
| 1 | **アプリ名・パッケージID・ストア上のブランド** | 個人用 BeanBase と同名にするか別名にするか。パッケージIDは公開後に変更不能 |
| 2 | **英語対応** | 母数10倍 vs 30画面の文言外部化の工数(収益化アイデア §9-1)。**v1.0 は日本語のみ、v1.1 以降で判断**が妥当 |
| 3 | **アフィリエイト導線** | 原価ゼロで相性は最良(収益化アイデア §6-1)だが、Amazon アソシエイト審査とステマ規制の広告表記が要る。v1.0 に入れるかは要判断 |
| 4 | **Firestore レガシー資産の扱い** | 回数カウンタに Firestore を使うなら、`FirestoreService` を復活させるのか新規に書くのか |
| 5 | **Pro での `model: opus` サブエージェントの可否** | T5-A14 で実測。使えない場合は §5 の「設計の先出し」を徹底する |
| 6 | **既存 `mainColorProvider`(メインカラー設定)と新デザイントークンの関係** | P2 のデザイントークン設計時に決める |
