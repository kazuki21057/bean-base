# 開発運用基盤設計 — 夜間自動実行(Windows タスクスケジューラ)

作成日: 2026-08-07 / 上位文書: [`リリース計画書.md`](./リリース計画書.md) / 対の文書: [`検証強化設計.md`](./検証強化設計.md)

> **本書の目的**: Pro プランの5時間枠を守りながら、ユーザーが寝ている間も開発が進む仕組みの設計。実装タスクは `docs/改修マスタープラン.md` §3 Phase 5 トラックA(T5-A9〜A12)。

---

## 1. 全体構成

```
Windows タスクスケジューラ(23:00 / 04:10 / 09:20)
        │
        ▼
tools/night_loop.ps1  ← ガード・前処理・後処理はすべてここ(LLM にやらせない)
        │
        ▼
claude -p "/night_loop" --model sonnet --permission-mode acceptEdits
        │
        ▼
.claude/skills/night_loop/SKILL.md  ← 無人実行専用の手順
        │
        ├─ implementer(実装)
        ├─ verifier / ui_verifier / adversary(検証、→ 検証強化設計.md)
        └─ 自動 push ゲート判定 → main へ push / PR 作成
```

**設計原則: 判断できることはスクリプトに、判断が要ることだけを LLM に。** ガード・スケジュール・ログ・ロックは PowerShell 側が確実に行い、LLM は「どのタスクを実装しどう直すか」だけを担う。

## 2. `tools/night_loop.ps1`(ラッパー)

### 2-1. 責務

| # | 責務 | 失敗時の挙動 |
|---|---|---|
| 1 | 多重起動ガード | 既に実行中なら即終了(ログのみ) |
| 2 | **有人セッション活動チェック** | 直近`activeSessionMinutes`分以内に会話活動があればスキップ |
| 2.5 | **Proプラン使用率ガード** | ゲートではなく記録専用(`.claude/night_usage_log.tsv`)。2026-08-13、ユーザー判断によりスキップ判定は撤廃 |
| 2.7 | **作業ツリー汚れガード** | 未コミットの変更があればスキップ+通知 |
| 3 | 週次予算ガード | 週の実行回数が上限を超えていればスキップ |
| 4 | `git pull --ff-only` | コンフリクト時は実行せず通知して終了 |
| 5 | ヘッドレス起動とログ保存 | 異常終了はログに残し通知 |
| 6 | 結果の通知 | セッション側の `PushNotification` が主。ラッパーはフォールバック |

### 2-2. 有人セッション活動チェック(本設計の要、2026-08-13改訂)

**旧方式(mtime)が失敗した経緯**: 当初は `~/.claude/projects/<プロジェクトslug>/*.jsonl`(transcript)の**最新更新時刻(mtime)**を「セッション活動の実測値」として判定に使っていた。しかし実機では、開いたままのClaude Codeセッションが**会話が無くても**transcriptを周期的に書き換えることが確認され、その書き換え周期(約5時間)が判定窓(5時間)とほぼ一致した結果、`night_loop.ps1` が2026-08-09〜13にかけて**4回連続で全スキップ**する障害が発生した(実測経過時間0.07/0.39/0.11/0.28時間、いずれも判定窓を下回り続けていた。詳細は`rules/lessons_archive.md`該当教訓、`docs/改修マスタープラン.md` T5-A12参照)。mtimeは人間・自動を問わず「ファイルが触られた」ことしか示さず、「会話があった」ことを保証しないため、代理指標として成立しないと判断した。

**新方式(会話エントリのtimestamp)**: transcript内の各行から `"timestamp":"..."` フィールド(ISO8601、UTC)を正規表現で抽出し、直近5ファイル・各ファイル末尾200行の範囲で最大値(＝直近の会話エントリ時刻)を取る。この時刻をローカル時刻に変換した上で現在時刻との差を分単位で計算し、`activeSessionMinutes`(既定45分)未満なら有人セッション中とみなしてスキップする。`ConvertFrom-Json` は使わず正規表現抽出にしているのは、transcriptに文字化け行が混在しパース例外を起こすことが確認されているため。UTC→ローカル時刻変換(`.ToLocalTime()`)を省略すると9時間ズレて判定が逆方向に壊れる。

```
$lastActivity = Get-LastConversationActivity -TranscriptDir $TranscriptDir
if ($null -ne $lastActivity -and ((Get-Date) - $lastActivity).TotalMinutes -lt $Config.activeSessionMinutes) {
    Log "直近${activeSessionMinutes}分以内に有人セッションの会話活動あり($lastActivity)。今回の発火をスキップする。"
    exit 0
}
```

> **プロジェクト slug は環境ごとに違う**(Windows は `C:\src\Claude\bean-base` 由来、Ubuntu は `/home/kzk/claude/bean-base` 由来)。**起動時に `~/.claude/projects/` を実測して解決する**か、スクリプト冒頭の定数に環境ごとの値を書く。ハードコードした値が外れると「常にスキップ」または「常に実行」になり、どちらも静かに壊れるので、**解決できなかった場合はスキップではなくエラー終了+通知**にする。

**Proプラン使用率ガード(2026-08-13新設、同日中に記録専用へ改訂)**: `usageGuardUrl`(既定 `http://localhost:3000/`、ローカル使用状況確認API)から5時間枠(`Current session`)・週次(`Current week`)の使用率%を取得する。**旧仕様(新設当日のみ)**: いずれかが`usageSessionMaxPercent`/`usageWeekMaxPercent`(既定85/90)以上ならスキップしていた。**現行仕様(2026-08-13、ユーザー判断により変更)**: スキップ判定は撤廃した。取得できた値は`usageLogEnabled`(既定true)が有効な限り`.claude/night_usage_log.tsv`(タブ区切り: タイムスタンプ・5時間枠%・週次%)へ追記するだけで、しきい値に達していても処理は継続する。API接続に失敗した場合は引き続き**fail-open**(処理続行、WARNログのみ、この場合は記録行も追記しない)とする——夜間ループが使用率APIの不調で恒久停止することを避けるため。`usageSessionMaxPercent`/`usageWeekMaxPercent`の2キーはゲート撤廃に伴い廃止(設定ファイルに残っていてもWARNログのみで無視される)。

**作業ツリー汚れガード(2026-08-13新設)**: `git status --porcelain` の出力が非空(未コミットの変更あり)ならスキップし、唯一この場合だけ通知を出す(人間の確認・コミット/退避を促すため)。

### 2-3. 週次予算ガード

Pro には5時間枠とは別に週次の上限がある。`.claude/night_runs.log`(1行1実行、ISO8601 タイムスタンプ)に追記し、直近7日の行数が上限(**既定15回(2026-08-13、12→15に変更。ユーザーは将来的な撤廃も検討中)**)を超えていたらスキップする。上限値は `tools/night_loop.config.json` で変更可能にする。

### 2-4. 起動コマンド

```powershell
claude -p "/night_loop" `
  --model sonnet `
  --permission-mode acceptEdits `
  --output-format stream-json `
  2>&1 | Tee-Object -FilePath ".claude\night_logs\$stamp.jsonl"
```

**権限モードについて(2026-08-08改訂、Web調査に基づく)**: 上記の `--permission-mode acceptEdits` は**不足**。`acceptEdits` が自動承認するのはファイル編集だけで、Bashコマンドは allowlist に無ければ止まる。無人実行の現在の推奨は **`dontAsk`** ——読み取り系と明示 allowlist は実行し、**それ以外はプロンプトせずに拒否する**(無人ループが応答待ちで固まらず、かつ勝手に危ないことをしない)。あわせて予算上限(`--max-budget-usd`)とターン上限で暴走を止める(**ターン上限は CLI オプションでは指定できない**。下記参照)。`--dangerously-skip-permissions` は採用しない(ホームディレクトリ全消失等の実被害が報告されており、プロンプト経由で入力された文字列がそのままコード実行につながる攻撃面になる)。

修正後の起動コマンド:

```powershell
claude -p "/night_loop" `
  --model sonnet `
  --settings ".claude\settings.night.json" `
  --permission-mode dontAsk `
  --max-budget-usd 20 `
  --output-format stream-json `
  --disallowedTools "<§4-4 の deny 相当>" `
  2> ".claude\night_logs\$stamp.err.log" | Tee-Object -FilePath ".claude\night_logs\$stamp.jsonl"
```

**stdout と stderr を分離する理由(2026-08-08、T5-A10 実装時に修正)**: 当初案の `2>&1 | Tee-Object` は、native exe の stderr を PowerShell が `NativeCommandError` としてラップするため、**`--output-format stream-json` の出力先である `.jsonl` に非 JSON 行が混入する**(T5-A10 で実機再現済み)。`git pull` 側で使っている `cmd /c '... 2>&1'` 方式での統合も検討したが、`--disallowedTools` のパターン文字列が `(` `)` `*` を含みクォートの組み立てが安全と判断できなかったため、**stdout は `.jsonl`、stderr は同名の `.err.log` へ分離する**方式を採る。`$LASTEXITCODE` は claude 自身の終了コードをそのまま取得できる。なお `.err.log` は生の stderr ではなく PowerShell のエラーレコード整形テキストになる(T5-A10 で実測)。朝これを読むときは複数行の整形が入る前提で見ること。

**`--max-turns` は claude CLI(2.1.225 で実測)に存在しないため採用できない。** ターン数の上限(夜間80、2026-08-13に40→80へ変更)は CLI では縛れず、`loop_guard.js`(T5-A11)とスキル側の自己判定で担保する。CLI 側の暴走防止は `--max-budget-usd` が担う(Pro プランでは API 課金が発生しないため効かない可能性があり、その場合の実効的な歯止めは loop_guard とゲートである)。

**`.claude/settings.night.json`(無人実行専用の権限プロファイル)は、ユーザー本人が設置する。** アシスタントは自分の権限設定を書き換えられない(自動モード分類器が拒否する)。これは制約ではなく前提で、**自分で自分の権限を広げられるエージェントの権限設定には意味が無い**。CI で人間が bot のクレデンシャルとポリシーを用意するのと同じ position。設置すべき内容は §4-4 を参照。

**このプロファイルの効き方**: `--settings` で渡してもプロジェクトの `.claude/settings.json` と**マージ**される(`allow` 配列は合算)。既存の project 設定には広い `Bash` / `PowerShell` の allow があるため、**実効的な安全装置は `allow` ではなく `deny`**(deny は allow に優先する)。2026年時点で deny ルールの不具合報告があるため、多層防御として `night_loop.ps1` 側でも `--disallowedTools` に同等の指定を渡す。**どちらも単独の防御線として信頼しない** —— 最後の砦は「無人実行でしか使わないアカウント/環境」と「main への push をゲートで縛ること」。

### 2-5. スケジュール

| 発火時刻 | 用途 | 既定 |
|---|---|---|
| 23:00 | 就寝前〜深夜枠 | 有効 |
| 04:10 | 深夜〜早朝枠 | 有効 |
| 09:20 | 朝枠(ユーザーが日中に使っていれば §2-2 の有人セッション活動チェックでスキップされる) | 設定で切替 |

**5時間ちょうどではなく5時間10分間隔**にするのは、枠の境界を確実に跨ぐため。タスクスケジューラは「PC がスリープしていたら起こす」を有効にし、実行アカウントはユーザー本人(`claude` の認証情報とリポジトリへのアクセス権が要る)。

**トリガー時刻の伝搬(2026-08-13追加、T5-A60)**: `night_loop.ps1`は起動時刻から発火枠(`2300`/`0410`/`0920`/`manual`)を判定し、環境変数`BEANBASE_NIGHT_TRIGGER`としてclaude子プロセスへ伝搬する。`/night_loop`スキルは`0410`・`0920`枠では、マスタープランの`⚠️ユーザー実施`等の承認待ちタスクのうち無人でも進められる準備作業を優先的に選ぶ(禁止事項の解除ではなく優先順位の変更のみ)。

## 3. `/night_loop` スキル(`.claude/skills/night_loop/SKILL.md`)

`full_loop` を無人実行向けに絞ったもの。**`full_loop` を書き換えるのではなく、別スキルとして新設する**(有人の `/full_loop` は従来どおり残す)。

### 3-1. `full_loop` との差分

| 項目 | `/full_loop`(有人) | `/night_loop`(無人) |
|---|---|---|
| タスク選定 | 依存が満たされた最上位を選ぶ | 同じ。ただし**S/M最大2件、またはLサイズ1件まで**(2026-08-13改訂)。「⚠️上位モデルで実施」は選ばず通知して終了。**04:10/09:20枠**(`BEANBASE_NIGHT_TRIGGER`)では承認待ちタスクの準備作業を優先 |
| 設計判断 | architect へ委譲して継続 | **継続しない。** 手を止めて `night_report.md` に「有人セッションが必要」と書いて終了 |
| デプロイ | ユーザーの明示的許可を得て実行 | **絶対にしない**(`firebase deploy` / Cloud Run デプロイ / Play Console 提出はすべて有人専用) |
| 本番データ操作 | 追加・更新は可、削除は要確認 | **読み取りのみ。書き込み・削除ともしない** |
| push | ユーザーの明示的許可を得て実行 | **自動 push ゲート(§4)を通過したときだけ main へ。** 落ちたら `night/<タスクID>` ブランチ + PR |
| 検証 | verifier 1体 | **verifier + ui_verifier + adversary**(→ 検証強化設計.md) |
| 終了時 | `NEXT_SESSION.md` 更新 | 同じ + **`night_report.md` を上書きして commit** |
| 通知 | チャット内 | **`PushNotification` を必ず送る**(ユーザーは画面を見ていない) |

### 3-2. 手順

1. **状況確認** — `.claude/loop_state.md` でしきい値超過を確認(夜間は $20 / ターン80、2026-08-13に$8/40から変更、§5)。`NEXT_SESSION.md` §2 と `docs/改修マスタープラン.md` §3 Phase 5 の未完了行を読む。読むファイルは `CLAUDE.md` §毎ループの読み取り最小セットに従う
2. **タスク選定** — `BEANBASE_NIGHT_TRIGGER`が`0410`/`0920`なら承認待ちタスクの準備作業を優先確認する。無ければ依存が満たされた最上位の**S/M/Lサイズ**タスクを選ぶ(S/Mは最大2件まで連続実施可、Lは1件のみ)。該当が無ければ §3-3 へ
3. **実装** — `implementer` へ委譲。設計判断が必要と判明したら**そこで中断**して §3-3 へ
4. **検証** — `verifier` を実行し、並行して `ui_verifier`(UI変更時)と `adversary` を**同一メッセージで起動**する
5. **自動 push ゲート判定**(§4)
6. **締め** — `NEXT_SESSION.md` 更新 → マスタープラン進捗表更新 → 新しい教訓があれば `rules/lessons_archive.md` + `rules/verification.md` インデックス → `night_report.md` 上書き → commit → §4 の判定に従って push
7. **通知** — `PushNotification` で1〜2文の要約を送る

### 3-3. 中断して終わる条件(新規タスクを発明しない)

以下のいずれかに該当したら、**新しいタスクを勝手に作らず**、`night_report.md` に理由を書いて通知し終了する。

- 着手できる S/M/L タスクが無い(全件が依存未充足、または「⚠️上位モデルで実施」指定しか残っていない)
- 実装中に設計判断(フィールド名・画面ID・文言・アルゴリズムの新規決定)が必要になった
- `implementer` が2回失敗した(3回目を同じやり方で試さない)
- しきい値(コスト・ターン・連続失敗)に到達した
- `git pull` でコンフリクトした

### 3-4. `night_report.md`(朝イチでスマホから読むもの)

**1画面に収まる長さ**で、毎回上書きする。commit するので **GitHub のモバイルアプリから読める**。

```markdown
# 夜間ループ報告 2026-08-08 04:10

- **タスク**: T5-B12 ローカルDBマイグレーション基盤
- **結果**: ✅ 完了 / main へ自動push済み(コミット abc1234)
- **検証**: verify.ps1 全green / integration_test 12件パス / adversary Critical 0(Major 1: 〇〇)
- **人がやること**: なし
- **次のタスク**: T5-B13(依存充足済み)
```

**失敗時のテンプレート**も同じ形。「人がやること」に具体的な依頼(判断・許可・実機確認)を1行で書く。

## 4. main への自動 push ゲート

### 4-1. 判定表

| # | 条件 | 判定元 | UI変更が無い場合 |
|---|---|---|---|
| 1 | `tools/verify.ps1` の全項目が green | スクリプトの JSON | 適用 |
| 2 | `integration_test` スモークが全パス | verifier | 適用 |
| 3 | `ui_verifier` が異常なしと報告 | ui_verifier | **判定対象外(スキップ)** |
| 4 | `adversary` の Critical 指摘がゼロ | adversary | 適用 |

**該当する条件すべてが満たされた場合のみ** `git push origin main`。

### 4-2. 落ちた場合

```
git checkout -b night/<タスクID>
git push -u origin night/<タスクID>
gh pr create --title "<タスクID> <要約>" --body "<ゲートのどの条件が落ちたか + 各エージェントの指摘>"
PushNotification("<タスクID> は自動pushゲートを通過しませんでした。PR #N を確認してください")
```

main には一切触れない。ユーザーは朝、スマホの GitHub アプリで PR を見て、マージするか差し戻すかを判断する。

### 4-3. なぜこの設計か

ユーザーの要求は「**全自動で進むほうが嬉しい**」と「**確実に検証できていることが前提**」の両方。この2つは、**クリーンなときは全自動・怪しいときだけ人間に上げる**という条件分岐で同時に満たせる。全件を PR にすると自動化の意味が薄れ、全件を main に入れると壊れた変更が入る。ゲートはその中間点を明示的に定義したもの。

### 4-4. `.claude/settings.night.json`(ユーザーが設置する)

**2026-08-08、ユーザー指示「定期実行するのに都度確認は意味が無い。世の中のやり方を調べて実装して」に対する回答。**

無人実行における確認の考え方は、有人セッションとは根本的に違う:

| | 有人セッション | 無人実行(夜間ループ) |
|---|---|---|
| 危険な操作の扱い | **その都度確認する**(人間が見ている) | **実行できなくする**(見ている人間がいない) |
| 同意の所在 | 操作の直前、チャット上 | **スケジュール登録した時点**(人間がこのプロファイルを設置した行為そのもの) |
| 主たる防御 | 確認プロンプト | 権限プロファイル(deny)+ 機械判定のゲート |

これは CI/bot の標準的な考え方と同じ。bot に「デプロイしていいですか?」と聞かせるのではなく、**bot のクレデンシャルにデプロイ権限を与えない**。同様に夜間ループでは `firebase deploy` / `clasp push` / `gh pr merge` / force push / `rm -rf` を **deny で不可能にする**。デプロイは朝、有人セッションでユーザーが判断して実行する。

以下を `.claude/settings.night.json` として設置する(**アシスタントは自分の権限設定を書き換えられないため、ユーザー本人が作成する**):

```jsonc
{
  // 夜間・無人実行(tools/night_loop.ps1)専用。有人セッションでは読み込まれない。
  // 実効的な安全装置は allow ではなく deny(project settings とマージされ、deny は allow に優先するため)。
  "permissions": {
    "defaultMode": "dontAsk",
    "deny": [
      // デプロイ: 本番反映は無人では一切させない。朝ユーザーが有人で実行する
      "Bash(firebase deploy*)", "Bash(npx firebase deploy*)", "Bash(npx -y firebase-tools* deploy*)",
      "PowerShell(firebase deploy*)", "PowerShell(npx firebase deploy*)",
      "Bash(clasp push*)", "Bash(clasp deploy*)", "Bash(clasp redeploy*)",
      "PowerShell(clasp push*)", "PowerShell(clasp deploy*)", "PowerShell(clasp redeploy*)",

      // 履歴の破壊・強制上書き(-f系は前方一致形を中心に列挙。理由は本テンプレート直後の注記を参照)
      "Bash(git push * --force*)", "Bash(git push --force*)",
      "Bash(git push * -f *)", "Bash(git push -f*)", "Bash(git push * -f)",
      "Bash(git reset --hard*)", "Bash(git clean -f*)", "Bash(git branch -D*)", "Bash(git rebase*)",
      "PowerShell(git push * --force*)", "PowerShell(git push --force*)",
      "PowerShell(git push * -f *)", "PowerShell(git push -f*)", "PowerShell(git push * -f)",
      "PowerShell(git reset --hard*)", "PowerShell(git clean -f*)",
      "PowerShell(git branch -D*)", "PowerShell(git rebase*)",

      "PowerShell(powershell -File tools\\verify.ps1*)", "Bash(bash tools/verify.sh*)",

```

**deny のパターンはワイルドカード前方一致で判定されるため、`git push * -f *` のような中間一致形は `git push -f origin main` を捕まえられない(T5-A10 の敵対的レビューで実測)。`-f` 系は前方一致形で列挙すること。**

**設置後に必ず T5-A12 の有人試走で実測すること。** 特に確認する点: (a) `dontAsk` で拒否されて止まる定型コマンドが無いか(あれば `allow` に足す) (b) deny が実際に効くか(`firebase deploy --help` 等の無害な形で1つ試す) (c) ゲート通過時に `git push origin main` が通るか。

**既知の弱点(承知のうえで受け入れる)**: プロジェクトの `.claude/settings.json` に広い `Bash` / `PowerShell` の allow があるため、deny に列挙し忘れた危険コマンドは素通りする。列挙漏れを完全に防ぐことはできないので、**最後の砦は「無人で触られて困るものを無人実行環境に置かない」**(本番クレデンシャルを別アカウントに分離する等)。これは §7 の失敗モードとして扱う。

## 5. `loop_guard.js` のしきい値調整

現行の `$24 / ループ`・`ターン30` は API 従量課金を前提にした値。**Pro プランでは「5時間枠をどれだけ食ったか」の代理指標**にすぎない。

| モード | コスト上限(代理指標) | ターン上限 | 連続失敗 |
|---|---|---|---|
| 有人(`/start`・`/full_loop`) | $24(従来どおり) | 30 | 3 |
| **夜間(`/night_loop`)** | **$20**(2026-08-13、$8から変更) | **80**(2026-08-13、40から変更) | **2** |

**2026-08-13、ユーザー判断によりProプラン使用率ガードをゲートとしては廃止したため、この上限の意味は「5時間枠温存」ではなく「暴走防止の安全弁」に変わった。1晩に最大2件のS/Mタスク、または1件のLタスクを許容する分、上限を引き上げた。**

旧理由(2026-08-08新設時点、参考として残す):
- **コストを下げる**理由: 1回の発火で枠を使い切ると、次の発火までの間ユーザーが使えなくなる。1晩に2〜3回まわす前提なので1回あたりを抑える
- **ターンを上げる**理由: 検証エージェントが3体になり、正常系でもターン数が増える。コスト側で縛れば十分
- **連続失敗を2回に下げる**理由: 無人では失敗の原因を人間が見ていない。3回目を試すより早く人間に上げたほうがよい

実装は `loop_guard.js` がループ識別子から夜間ループを判別して別のしきい値を使う形(判別できない場合は安全側=夜間のしきい値を使う)。

## 7. 想定される失敗モードと対策

| 失敗モード | 対策 |
|---|---|
| 権限プロンプトで無言のまま停止する | 段階3で実測。`--allowedTools` を明示指定 |
| slug 解決に失敗し、5時間チェックが常にスキップ/常に実行になる | 解決失敗時はエラー終了+通知(静かに壊れさせない) |
| コンテキストが肥大して単価が2倍になる | 1発火 = 1セッションなので `/full_loop` の `/loop` 運用時のような積み上がりは起きない。加えて $20 のしきい値で止まる(2026-08-13、$8から変更) |
| エミュレータが起動しない/固まる | `verifier` が2〜3回試して止め、事実を報告。ゲートは条件2で落ちるので main には入らない |
| 同じタスクを毎晩繰り返し着手する | マスタープランの進捗表更新を締め処理に含める(commit されるので次回は完了扱いになる) |
| PC がスリープして発火しない | タスクスケジューラの「タスクを実行するためにスリープを解除する」を有効化 |
| 夜間ループが `NEXT_SESSION.md` を壊す | 締め処理は `full_loop` と同じ手順(古い節をアーカイブへ移す)を踏襲。commit されるので差分で追える |
