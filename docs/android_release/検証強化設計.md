# 検証強化設計 — main への自動 push を成立させる検証体制

作成日: 2026-08-07 / 上位文書: [`リリース計画書.md`](./リリース計画書.md) / 対の文書: [`開発運用基盤設計.md`](./開発運用基盤設計.md)

> **本書の目的**: 夜間の無人実行が main へ直接 push してよいと言える検証体制を設計する。ユーザー指示「検証エージェントの性能を向上させたい。トークン増は許容。**見直し方はしっかり調査し、成果の出るものを選んで**」への回答。

---

## 1. 調査: 何が検証をすり抜けてきたか

### 1-1. 調査方法

このリポジトリには `rules/lessons_archive.md` に **115件の教訓(L01〜L115)** が蓄積されている。これを「**検証をすり抜けて本番/ユーザー報告まで到達した欠陥**」という観点で読み直した。一般論のベストプラクティスではなく、**このプロジェクトで実際に起きたこと**を根拠にする。

### 1-2. 結果: 逸出は8パターンに集約される

| # | 逸出パターン | 実例(教訓番号) | `analyze` で捕まるか | `flutter test` で捕まるか |
|---|---|---|---|---|
| 1 | **契約/スキーマのズレが静かに null になる** | L90(keyMapの列名が本番と違ってもエラーにならず常に null)、L16、L42 | ✗ | ✗(fake が本物と違う契約を持つため) |
| 2 | **サイレントな fallback が失敗を隠す** | L102(画像URLは入っているのに `<img>` は onerror。プレースホルダーへのフォールバックはコンソールに何も出さない) | ✗ | ✗ |
| 3 | **実データの意味論の取り違え** | L95(湯量係数が固定15g割り)、L107、L112(加算時間の意味を取り違え、点灯区間が常に1ステップ先) | ✗ | ✗(期待値自体が間違っているため緑になる) |
| 4 | **release ビルドでのみ再現する** | L54(Flutter Web の不具合は debug では再現せず release で出る)、L55 | ✗ | ✗(debug しか見ていない) |
| 5 | **部分的な日本語化の残り** | L41(タイトルだけ日本語で本文が英語のダイアログが本番に残った) | ✗ | ✗ |
| 6 | **同症状の再修正が症状の一部しか直していない** | L112(T3-79 で直したはずの注湯ハイライトが T3-80 で再発。前回は症状の一部しか直していなかった) | ✗ | ✗(前回追加した回帰テストごと間違っている) |
| 7 | **設計書が呼び出し元を過小把握している** | L92(「呼び出し元はここだけ」という設計書の記述が誤り)、L101 | △(削除なら error) | ✗ |
| 8 | **マスタ横展開漏れ** | CLAUDE.md 規約(豆だけ直してグラインダー/ドリッパー/フィルター/メソッドを忘れる) | ✗ | ✗ |

### 1-3. 結論

**8件すべてが「`flutter analyze` と `flutter test` が緑でも通過する」。** 現在の `verifier` はこの2つ+ブラウザ目視のチェックリストを走らせるだけなので、**チェックリストを強化しても8パターンのどれも捕まらない**。

したがって「検証エージェントを賢くする」のではなく、**捕まえ方の種類を増やす**必要がある。

## 2. 設計: 3層で対処する

**効果の大きい順**に並べる。層1が最も効果が大きく、しかもトークンを減らす。

| 層 | 手段 | 狙う逸出パターン | トークンへの影響 |
|---|---|---|---|
| 層1 | 決定論的な検証をスクリプトへ降ろす | #4, #7(一部) | **大幅減** |
| 層2 | 自動回帰スイート(エミュレータ + golden) | #2, #3(一部), #8(一部) | 微増 |
| 層3 | 敵対的レビュー(専任エージェント) | #1, #2, #3, #5, #6, #7, #8 | 増(許容) |

---

## 3. 層1: 決定論的な検証をスクリプトへ降ろす(最優先)

### 3-1. なぜこれが最優先か

現状、`verifier` は `flutter analyze` と `flutter test` を**自分で叩いて出力を読んでいる**。この出力は1回で 7k〜13k 文字あり、**以降のリクエスト全部に課金され続ける**(`rules/verification.md` の既存の指摘。だからこそ「短出力形」の運用が既に導入されている)。

つまり現状は、**最も機械的で判断の余地がない作業に、最も高いトークンを払っている**。ここを外に出せば、**検証エージェントを3体に増やしてもトークンは増えない。** これが本設計を成立させる土台。

### 3-2. `tools/verify.ps1` / `tools/verify.sh`

**入力**: 対象エディション(personal / public)、変更ファイル一覧(`git diff --name-only`)
**出力**: **JSON 1つ**(標準出力)+ 詳細ログはファイルへ

| 検査項目 | 内容 | 狙い |
|---|---|---|
| `analyze` | `flutter analyze` の issue 件数を `.claude/analyze_baseline.txt` と比較。増えていたら fail | 既存運用の踏襲 |
| `test` | `flutter test` 全パス | 既存運用の踏襲 |
| `test_coverage_delta` | 変更した `lib/` ファイルに対応するテストが増えているか。無ければ **warning**(fail にはしない) | テストなしの実装を可視化 |
| `build_apk_release` | `flutter build apk --release -t lib/main_public.dart` | **逸出パターン#4** への直接対策 |
| `build_web_release` | `flutter build web --release` | personal 版のリグレッション防止 |
| `golden` | golden テストの差分ゼロ | 視覚回帰(層2と対) |
| `codegen_clean` | `dart run build_runner clean` → `dart run build_runner build --force-jit`(タイムアウト600秒)後に `git diff --exit-code` | `.g.dart` 再生成漏れ(L23) |
| `secret_scan` | `gemini_api_key` 等の値がステージ済み差分に含まれていないか | 秘密情報のコミット防止 |

**出力例**:

```json
{
  "ok": false,
  "checks": {
    "analyze":            {"ok": true,  "baseline": 12, "current": 12},
    "test":               {"ok": true,  "passed": 372, "failed": 0},
    "test_coverage_delta":{"ok": true,  "warning": "lib/db/migrations.dart に対応テストなし"},
    "build_apk_release":  {"ok": false, "summary": "R8: missing_rules for com.google.android...", "log": ".claude/verify_logs/20260808_0410_apk.log"},
    "build_web_release":  {"ok": true},
    "golden":             {"ok": true,  "diff_count": 0},
    "codegen_clean":      {"ok": true},
    "secret_scan":        {"ok": true}
  }
}
```

**LLM はこの JSON だけを読む。** 失敗した項目があるときだけ、対応する `log` パスを読みに行く。

### 3-3. 静的解析ルールの強化(ほぼ無料で逸出パターン#2 に効く)

`analysis_options.yaml` に以下を追加する。**サイレントな fallback は書いた瞬間に lint で落ちる**ようになり、`adversary` が見るべき量が減る。

- `avoid_catches_without_on_clauses` — 何でも握りつぶす catch を禁止
- `unawaited_futures` — 投げっぱなしの非同期処理
- `avoid_empty_else`
- `always_use_package_imports`(循環 import 事故 L51 の予防にも効く)

既存コードに大量の違反が出る場合は、**新規ファイルにのみ適用する運用**(baseline 方式)から始める。

## 4. 層2: 自動回帰スイート

### 4-1. Android エミュレータ上の `integration_test` スモークスイート

**現状の問題**: ブラウザ目視(`claude-in-chrome`)は L08 / L38 / L80 / L98 / L103 が示すとおり**この環境で慢性的に不安定**で、スクロールが効かない・ビューポートが固定される・拡張が未接続になるといった事象に毎回ぶつかっている。高コストかつ結果が不確実で、**無人実行の判定材料にはできない**。

**対策**: 起動 → 記録(抽出→評価)→ 保存 → 一覧に反映 → インサイト表示 → 設定 の一筆書きを `integration_test` で自動化し、エミュレータ上で毎回実行する。

- **これが夜間の無人実行を成立させる前提条件**。「アプリが起動して主要導線が通る」ことを人間の目に頼らず言えるようにする
- パターン#2(サイレント fallback)にも効く: 画像が出ない・データが空になるといった症状は、目視では見落とすが**アサーションなら落ちる**
- パターン#8(マスタ横展開漏れ)にも部分的に効く: 5マスタすべての一覧→詳細→編集をスイートに含める

### 4-2. golden テスト

**「全画面を一から新規デザイン」する以上、視覚回帰を人間の目に頼ると必ず破綻する。**

- **共通コンポーネント単位**で golden を撮る(カード/リスト行/空状態/ローディング/エラー/ボトムシート)。画面単位より安定し、壊れた原因も特定しやすい
- **ライト/ダーク両方**を撮る
- 差分が出たら fail し、`ui_verifier` が「意図した変更か」を判定して人間に見せる。**LLM に golden を自動更新させない**(更新を許すと視覚回帰の検出機能そのものが無効化される)

**フロントエンド重視の要件に対して、最も安価で最も効く投資。**

## 5. 層3: 敵対的レビュー(エージェント体制の再編)

### 5-1. `verifier` を3体に分割する

| エージェント | 責務 | 修正権限 | モデル | 実行条件 |
|---|---|---|---|---|
| `verifier`(改) | `tools/verify.ps1` を実行し JSON を報告。**失敗したときだけ**該当ログを読む。エミュレータで `integration_test` を実行 | なし | sonnet | 毎回 |
| `ui_verifier`(新) | エミュレータでアプリを起動し、**変更した画面を実際に操作して**スクショ判定 | なし | sonnet | UI ファイルに変更があったとき |
| `adversary`(新) | `git diff` と設計書だけを渡し、**この変更が壊しうるもの**を仮説駆動で探す | なし | sonnet | 毎回 |

**3体とも「事実と指摘のみ。修正も原因推定の断定もしない」**(現行 `verifier` の絶対規則5を継承)。判断は親セッションが行う。

### 5-2. `ui_verifier` の見るもの

チェックリストは逸出パターンと現場の教訓に対応させる。

1. **Overflow**(黄黒ストライプ)が出ていないか
2. **文字化け/豆腐(⊠)** — ただし L104 のとおり初回描画時の一過性がありうる。**2〜3秒待って再描画してから判定**する
3. **部分英語**(逸出パターン#5)— SnackBar / AlertDialog / エラー文言 / 空状態の文言
4. **タップ領域** — 48dp 未満の操作要素がないか
5. **ダークモード** — 両モードで判読できるか
6. **空状態・エラー状態・ローディング状態** — 3つとも実際に表示させる(正常系だけ見ない)
7. **画像が実際に表示されているか**(逸出パターン#2 / L102。「URL が入っている」と「画像が出る」は別問題)

### 5-2a. `ui_verifier` の実装詳細(T5-A4 設計、2026-08-09)

§5-2 のチェックリストを「エミュレータ上で実際に実行できる手順」まで落とした節。**implementer はこの節だけを見れば `ui_verifier` を実装できる**ことを目標にする。

#### A. 決定事項サマリ

| # | 論点 | 決定 | 根拠 |
|---|---|---|---|
| 1 | 操作方法 | **画面の縦横に対する比率(0.0〜1.0)でのタップ**を第一手段とする。`uiautomator dump` は補助(取れたら使う、取れなければ比率タップへフォールバック) | Flutter は 1つの `FlutterView` に描画するため、UIAutomator から Widget が個別ノードとして見えるかは環境依存。比率タップは Flutter の実装に依存せず必ず動く。詳細は §H |
| 2 | スクショの撮り方 | `adb shell screencap -p /sdcard/...` → `adb pull` で PNG を取得し、`Read` ツールで画像として見る。**`adb exec-out ... > file.png` は使わない** | PowerShell 5.1 の `>` はバイナリを壊す(テキストとして再エンコードされる)。`adb pull` はファイルコピーなので安全 |
| 3 | 文字化け判定の待機 | `-Shot` が既定で **2.5秒待ってから**撮影。さらに豆腐が見えたときだけ **3秒後にもう1枚**撮り、2枚目でも残っている場合のみ「指摘あり」 | L104(初回描画のみの一過性がある)。1枚で断定しない |
| 4 | ツール許可 | `Read, Grep, Glob, PowerShell, ToolSearch`(**`Bash`・`Write`・`Edit` は与えない**) | `Write`/`Edit` が無いことが「修正権限なし」の担保。`Bash` を外すのは、Windows 前提の `ui_probe.ps1` を2種類のシェルで叩き分けさせないため(L127 の BOM/バイナリ事故の予防) |
| 5 | 対象画面の特定 | **親が画面ID(`AppScreen.code`)を渡すのが原則**。渡されないときは `git diff --name-only` から §E の手順で機械的に導出する。上限3画面 | `lib/routing/screen_registry.dart` が「画面Widget クラス名 → `AppScreen`」の対応表になっており、機械的に引ける |
| 6 | 対応OS | **Windows のみ**(`tools/ui_probe.ps1`)。Ubuntu 版(`.sh`)は作らない | 本設計書に `ui_verifier` の OS 要件の記述は無い。開発環境も夜間ループ(`tools/night_loop.ps1`)も Windows で、AVD `beanbase_test` の実体も Windows 側にしか無い。必要になった時点で別タスクにする |

#### B. 前提となるビルド構成(**debug APK 必須**)

`ui_verifier` は **debug ビルドの APK** を対象にする。release/profile では成立しない。

- **overflow の黄黒ストライプと `A RenderFlex overflowed by ... pixels.` のログは `assert(() { ... }())` の中にある**(`C:\src\flutter\packages\flutter\lib\src\rendering\flex.dart:1335-1372` の `RenderFlex.paint`、および `debug_overflow_indicator.dart:259-276` の `FlutterError.reportError`)。assert が無効な release/profile では**ストライプもログも一切出ない**ため、§5-2 の項目1 が原理的に検査できない。
- `android/app/src/main/AndroidManifest.xml` には `INTERNET` 権限が無く、`INTERNET` は `src/debug` と `src/profile` のマニフェストにしかない。**release APK では GAS/Drive/Gemini に接続できない**(これはトラックB=公開版リリースで別途対処が必要な事項。T5-A4 の範囲外だが記録として残す)。
- **debug ビルドでも既定で structured errors が有効**なため、`FlutterError` は logcat には出ず VM Service の `Flutter.Error` 拡張イベントへ送られる。`flutter run` でアタッチしていない単独起動(`ui_probe.ps1` の運用)ではこのイベントを受信する側がいないため、overflow/exception 系のログが logcat に一切出力されない。`--dart-define=flutter.inspector.structuredErrors=false` を付けてビルドすることで解消する(T5-A36 の実測で確認)。

したがって `-Prepare` は `flutter build apk --debug --dart-define=flutter.inspector.structuredErrors=false` を使う。

#### C. `tools/ui_probe.ps1`(新設)の仕様

`tools/emulator.ps1` と同じ書式(switch パラメータ + `Get-AndroidSdkRoot` で SDK 解決)で実装する。エミュレータの起動/停止そのものは `tools/emulator.ps1` を呼び出して再実装しない。

**共通の出力規約**: 各サブコマンドは**標準出力に1行の JSON だけ**を出す(進捗メッセージは `Write-Host` ではなく `Write-Verbose`/stderr へ)。LLM が読むのはこの1行だけ。

| サブコマンド | 引数 | 動作 | 標準出力(1行 JSON) |
|---|---|---|---|
| `-Prepare` | `[-SkipBuild] [-ClearData] [-AvdName beanbase_test]` | ①`tools/emulator.ps1 -Status` で起動確認、未起動なら `-Start` ②`-SkipBuild` でなければ `flutter build apk --debug --dart-define=flutter.inspector.structuredErrors=false`(タイムアウト900秒) ③`adb install -r build/app/outputs/flutter-apk/app-debug.apk` ④`adb shell cmd uimode night no`(ライト固定) ⑤アニメ無効化: `adb shell settings put global window_animation_scale 0` / `transition_animation_scale 0` / `animator_duration_scale 0` ⑥`-ClearData` 指定時のみ `adb shell pm clear com.example.bean_base` ⑦`adb logcat -c` ⑧`adb shell am force-stop com.example.bean_base` ⑨`adb shell am start -W -n com.example.bean_base/.MainActivity` ⑩6秒待機 ⑪セッションディレクトリ作成 | `{"ok":true,"session":".claude/ui_verify/20260809_213000","serial":"emulator-5554","width":1080,"height":2400,"density":440,"tap48dp_px":132,"launch_ms":3412}` |
| `-Shot` | `-Name <名前> [-DelaySec 2.5] [-Session <dir>]` | `-DelaySec` 秒待機 → `adb shell screencap -p /sdcard/uiv.png` → `adb pull` → 端末側を `rm` | `{"ok":true,"file":".claude/ui_verify/<session>/03_010_initial.png"}` |
| `-Tap` | `-X <0..1> -Y <0..1>` | `input tap [round(X*width)] [round(Y*height)]` → 1.2秒待機 | `{"ok":true,"px":540,"py":2256}` |
| `-Swipe` | `-X -Y -X2 -Y2 [-DurationMs 300]` | `input swipe px py px2 py2 durationMs` → 1.0秒待機 | `{"ok":true,"from":[540,1680],"to":[540,720]}` |
| `-Back` | なし | `input keyevent 4` → 1.0秒待機 | `{"ok":true}` |
| `-Log` | `[-Session <dir>]` | `adb logcat -d -v time` を取得し**全文をセッションへ保存**した上で、下記パターンに一致した行だけを抽出 | `{"ok":true,"file":"...\|logcat_flutter.txt","hits":{"overflow":2,"exception":0,"antigravity_error":0,"image":1},"lines":["A RenderFlex overflowed by 23 pixels on the right.", ...最大20行]}` |
| `-Dump` | `-Name <画面ID> [-Session <dir>]` | `adb shell uiautomator dump /sdcard/ui.xml` → `pull` → `<node ` の数を数える | `{"ok":true,"nodes":47,"file":"...\|dump_010.xml","usable":true}`。**`nodes<=2` なら `"usable":false`**(Flutter の semantics が露出していない=比率タップへフォールバック) |
| `-Net` | `-State on\|off` | `off`: `adb shell svc wifi disable` + `adb shell svc data disable` / `on`: 両方 `enable` | `{"ok":true,"state":"off"}` |
| `-Info` | なし | `wm size` / `wm density` / `dumpsys window \| mCurrentFocus` | `{"ok":true,"width":1080,"height":2400,"density":440,"focus":"com.example.bean_base/.MainActivity"}` |

`-Log` の抽出パターン(正規表現、大文字小文字を区別しない):

```
A Render\w+ overflowed by
EXCEPTION CAUGHT BY
Unhandled Exception
\[Antigravity\].*(エラー|失敗|Error|Exception)
NetworkImageLoadException|HttpException|SocketException|FormatException
is not a subtype of type
```

**実装上の注意(必ず守る)**:
- `.ps1` は **UTF-8 BOM 付き**で保存する。BOM 無しだと PowerShell 5.1 が日本語コメントを構文エラーにする(L127、T5-A6 で実際に踏んだ)。
- `adb` の出力が一時的に空文字になることがあるので、`.Trim()` の前に null チェックを入れる(同じく L127)。
- `-Session` 省略時は `.claude/ui_verify/` 配下の**更新日時が最新のディレクトリ**を使う。
- スクショの連番 `NN` は、セッションディレクトリ内の既存 `*.png` 数 + 1 を2桁ゼロ埋めで採番する。

#### D. 成果物の保存先と命名規則

```
.claude/ui_verify/<yyyyMMdd_HHmmss>/     ← -Prepare が作るセッションディレクトリ
    device.json                          ← -Prepare の出力(解像度・密度・48dp相当px)
    01_090_initial.png                   ← <連番2桁>_<画面ID>_<状態>.png
    02_090_redraw.png
    03_010_loading.png
    04_010_offline.png
    dump_010.xml
    logcat_flutter.txt
```

`<状態>` に使う語は次に固定する: `initial` / `redraw`(2.5秒後の再撮影) / `loading` / `empty` / `offline` / `scrolled` / `dark`。

**`.gitignore` に `.claude/ui_verify/` を追記する**(実行のたびに生成される一時ファイル。既存の `.claude/verify_logs/` と同じ扱い)。

#### E. 対象画面の特定手順

**親から画面ID(`010` 等)または画面名が渡されていれば、それに従う(自分で広げない)。** 渡されていない場合のみ以下を実施する。

1. `git diff --name-only`(引数で範囲が渡ればそれを使う)で変更ファイルを取得する。
2. `lib/screens/**`・`lib/widgets/**`・`lib/layout/**` 以外は無視する。
3. `lib/screens/xxx_screen.dart` の場合: そのファイルの `class` 名を `Grep` で取り、`lib/routing/screen_registry.dart` を同じクラス名で `Grep` して直前の `case AppScreen.<名前>:` を得る。その `<名前>` を `lib/routing/app_screen.dart` で `Grep` すると `('010', '豆管理(カード)')` のように**画面IDと日本語名**が取れる。

5. 対象が4件以上になったら、**`git diff --stat` の変更行数が多い上位3画面**に絞る。報告に「対象が N 件あったため上位3画面のみ実施」と明記する。

#### G. 7項目の判定手順

#### H. 未検証の仮説(実装時に1回だけ実測して本節に追記する)

- **仮説(未検証)**: Flutter アプリでも `uiautomator dump` が semantics ノード(`text=`・`bounds=`)を返す。**検証方法**: `-Prepare` 後に任意の画面で `-Dump` を1回実行し、`nodes` の値を見る。`nodes<=2`(`FlutterView` 単体しか出ない)なら仮説は棄却で、項目3・4は目視推定に落とす。**結果をこの節に追記すること**(implementer の実装タスク6)。
- 仮説が棄却されても `ui_verifier` は成立する(比率タップとスクショ目視だけで7項目中5項目は判定できる)。**`-Dump` に依存する設計にはしない。**

**実測結果(T5-A4 implementer、2026-08-09)**: **仮説は棄却**。`com.example.bean_base`(BeanBase本体、パッケージ名で確認済み)に対して `-Dump` を実行したところ `nodes=5` を得た(内訳: `DecorView`相当の `FrameLayout` → `LinearLayout` → `content` の `FrameLayout` → **`FlutterView` に相当する `FrameLayout`(子ノード無し、`focusable="true"`)** → `statusBarBackground` の `View`。5ノードは`<=2`より多いが、**5ノードすべて `text=""`・`content-desc=""` で、実際のFlutterウィジェット(ボタン・テキスト・カード等)に対応するノードは1つも無い**。つまり「AndroidのActivity標準の入れ物(4ノード程度)+ Flutter描画面そのものを表す不透明な1ノード」が常時存在するため、`nodes<=2` という当初の見積りは**ベースラインの過小評価**であり、実際の閾値は「そのActivityの標準的な入れ物ノード数(実測4)+ Flutter描画面1ノード」程度になる。**実装済みの `-Dump` は設計書§Cの記載どおり `nodes<=2` を`usable`判定の閾値にしている**(この値の変更は設計判断のため implementer からは行わず、閾値の要修正は上位モデルへの報告事項とする)。なお計測はエミュレータの資源不足によりFlutterのスプラッシュ画面(起動直後の`am start -W`がタイムアウトした状態)でしか安定して再現できなかった(`.claude/ui_verify/20260809_091442/01_001_dump_target.png`・`dump_001_via_script.xml`)。ただしFlutterはActivity内に単一のレンダリングサーフェスとして描画するため、フル読み込み後の画面でも「Flutter描画面が1個の不透明ノードとして見える」という構造自体は変わらないと考えられる(未確定、環境安定時に再測定が望ましい)。**結論として項目3(部分英語)・4(タップ領域48dp)は目視推定に落とすほうが安全**——`usable:true`になっても`text=`/`bounds=`にFlutterウィジェット個々の情報は乗らない可能性が高い。

#### B. 再現実験(architect が3回実施)と、その結果

いずれも「起動 → ブート完了待ち → (必要なら)`install -r` → `am start -W` → プロセス生存監視」という同一手順。

| # | 起動オプション | 結果 |
|---|---|---|
| A | `-no-snapshot -gpu swiftshader_indirect -feature -Vulkan -no-boot-anim` | ブート成功 → APK 再インストール成功 → `am start` TotalTime 5925ms → **60秒後も生存**。スクリーンショット取得成功 |
| B | `-no-snapshot` のみ(GPU は既定 = lavapipe Vulkan) | ブート成功 → アイドル30秒生存 → `am start` 後 **30秒生存** |
| C | **現行 `tools/emulator.ps1` と完全に同一**(`-netdelay none -netspeed full` のみ) | ブート成功 → アイドル30秒生存 → `am start` 後 **40秒生存** |

**結論: 本日は3回とも再現しなかった。したがってクラッシュは起動オプションに対して決定論的ではなく、間欠的である。** 「Vulkan(lavapipe)を無効化すれば直る」は現時点では **仮説(未検証)** であり、事実として書いてはならない。

失敗した9回と実験3回の間で説明のつく差分は次の3点(いずれも **仮説(未検証)**):

1. 失敗時は `-Prepare` が **エミュレータを起動したまま `flutter build apk --debug` を実行**していた(Gradle/Kotlin デーモンが同時にCPUを占有)。完全ソフトウェアGPU(lavapipe/SwiftShader の JIT)は高負荷時に不安定になりうる。
2. 失敗時は毎サイクル 163MB の debug APK を `install -r` していた。
3. 失敗時は**クラッシュ後の後始末(孤児プロセス・ロックの掃除)をせずに即座に次の起動を掛けていた**。

#### C. 対策の方針

(1) 容疑者を減らす → (2) 落ちたことを**数秒で**検知して安く諦める → (3) 落ちても1回だけ自動で立て直す → (4) そもそもエミュレータに依存しない判定へ移す。**「起動を安定させる」だけを狙うと、間欠故障なので効果を証明できない。「落ちたときの損失を小さくする」ほうが確実に効く。**

#### D-1. AVD を作り直す(最優先、破壊的操作なし)

現状の `Invoke-Prepare`(`tools/ui_probe.ps1:310-400`)は、**手順③〜⑨のすべての `adb` 呼び出しを `| Out-Null` で捨てており、終了コードも見ていない**(`:350-372`)。そのためエミュレータが途中で死んでも、最後の `Get-DeviceInfoOrFail`(`:383`)まで一切気付かない。`flutter build apk --debug` のタイムアウトが900秒あるため、**最悪15分待ってから `ok:false` が返る**。9回の失敗が高コストになった直接の原因はここ。

#### D-4. エミュレータへの依存そのものを減らす

- **項目1(Overflow)はエミュレータ不要で機械判定できる。** widget test 内で `FlutterError.onError` を差し替え、`A RenderFlex overflowed` を含む例外が飛んだらテストを fail させる。`tester.view.physicalSize` / `devicePixelRatio` を 360x690 / 411x914 / 320x690 の3サイズに変えて各画面を pump すれば、実機解像度ごとの overflow を CI 相当で検出できる。**T5-A7(`integration_test`)/ T5-A8(golden)の範囲に含めること。** これが入れば `ui_verifier` がエミュレータで見る必要のある項目は 2 / 3 / 6 / 7 の4つに減る。
- **`ui_verifier` の起動条件を絞る**: `lib/screens/**`・`lib/widgets/**`・`lib/layout/**` の変更があり、**かつ見た目に関わる変更**のときだけ。夜間ループでは `-Prepare` が2回失敗した時点でその夜は `ui_verifier` を起動しない(`night_loop` 側のフラグ)。

#### E. 検証観点(この対策が効いたと言える条件)

1. **安定性**: 新 AVD で `emulator.ps1 -Start` → `ui_probe.ps1 -Prepare -SkipBuild` → `-Shot` を **連続5回**実行し、5回とも `ok:true`。判定は主観ではなく **`Get-WinEvent -FilterHashtable @{LogName='Application'; Id=1000; StartTime=<開始時刻>}` で `qemu-system-x86_64.exe` の APPCRASH が0件**であることで行う。
2. **安く諦められること**(こちらが本命): `-Prepare` の実行中に手動で `taskkill /IM qemu-system-x86_64.exe /F` を撃ち、**10秒以内**に `{"ok":false,"error":"device_lost",...}` が返ること。現状は最大900秒以上かかる。
3. **偽陽性が消えること**: 新 AVD(1080x2400 / 420dpi)でダッシュボード(001)を撮影し、**本調査で 320x640 のときに観測された「今日のおすすめレシピ」カードの `RIGHT OVERFLOWED BY 21 PIXELS` が出ないこと**。新 AVD でも出るなら実バグなので別タスクに切り出す。
4. **T5-A4 の完了条件**(設定画面 090 に意図的な overflow を入れて `ui_verifier` が「指摘あり」を返し、仕込んでいない画面では「該当なし」)を再実行して通ること。

#### F. 本調査で副次的に判明したこと

1. **320x640dp のダッシュボードで実際に overflow が発生している**(`RIGHT OVERFLOWED BY 21 PIXELS`、「今日のおすすめレシピ」カード)。現行 AVD の異常な画面サイズに起因する可能性が高い。実機相当解像度での再確認は §E-3。
2. **Android では豆腐(⊠)が観測されなかった**。日本語のラベル(ダッシュボード / ホーム / 履歴 / マスター / レシピ / 統計)・豆名・説明文・アイコンとも正常に描画された。§5-2a §G の項目2「Android での再現性は未確認」に対する部分的な回答(1サンプルのみ、確定ではない)。
3. **`ui_probe.ps1` の仕組み自体は成立している**。エミュレータが生きていれば、APK インストール → 起動 → スクリーンショット取得 → 目視判定まで一通り機能することを実測で確認した。残る障害はエミュレータの安定性だけである。

**出力形式**: `Critical` / `Major` / `Minor` の3段階。各指摘に **(a) 何が壊れうるか (b) 根拠となるコード位置 (c) 確認方法** を書く。

- **Critical** = そのまま main に入ると本番/ユーザー体験が壊れる
- **Major** = 壊れる可能性があるが条件付き
- **Minor** = 規約違反・可読性

**Critical が1件でもあれば自動 push しない**(→ 開発運用基盤設計.md §4)。

## 6. 検討したが採用しなかったもの

「効果の出るものを選ぶ」ためには、採らなかったものとその理由も残す。

| 案 | 不採用の理由 |
|---|---|
| **ミューテーションテスト** | テストの質を測る手段としては正しいが、Flutter/Dart のツール成熟度が低く、実行時間がループ1回の予算に収まらない |
| **全画面の E2E 網羅** | 保守コストが本体開発を上回る。**スモーク一筆書き+コンポーネント golden** のほうが費用対効果が高い |
| **LLM に同じ機能を2回実装させて突き合わせる** | トークンが倍かかるうえ、同じモデルは同じ誤解をするため独立性が担保されない |
| **検証エージェントをさらに増やす(4体・5体)** | 逸出パターン8件に対して層1〜3で被覆できており、追加は重複になる。**役割が重なるエージェントは互いの指摘を薄める** |
| **`verifier` に修正権限を与えて自己修復させる** | 検証と修正を同じエージェントが持つと自己検証バイアスが復活する。役割分離を崩さない |
| **`adversary` を上位モデルにする** | 効果は上がりうるが Pro での可用性が不確実。まず sonnet + **具体的なチェックリスト**で運用し、逸出が続くなら見直す |

## 7. トークンへの影響と検証

**エージェントは1体→3体+researcher に増えるが、1ループのトークンは減る見込み。**

| 要因 | 影響 |
|---|---|
| 層1により `analyze`/`test`/`build` の生出力(毎回7k〜13k文字、**以降の全リクエストに課金**)が JSON 1つに | **大幅減** |
| `ui_verifier` / `adversary` はサブエージェントなので**親のコンテキストに積み上がらない**(親に返るのは要約のみ) | 中立 |
| `ui_verifier` と `adversary` を**同一メッセージで並列起動** | 待ち時間の相殺 |
| ブラウザ目視の試行錯誤(L08/L38/L80/L103 でのリトライ)が `integration_test` に置き換わる | 減 |

**トラックA 完了後の最初の3ループで実測し、`docs/token_optimization_design.md` §7 に記録する**(既存の計測運用に乗せる)。悪化していたら `adversary` の起動条件を「差分が一定行数を超えたときだけ」に絞る。
