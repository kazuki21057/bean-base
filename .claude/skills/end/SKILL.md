# end — 日次ループのセッション終了

BeanBase 2.0 の「日次改修ループ」(`CLAUDE.md` §日次改修ループ運用ルール) における、1ループの締めくくり。停止時の作法は必ずこの順序で行う。

## 手順

1. **`NEXT_SESSION.md` を更新する**
   - 新しい「当日やったこと」節を先頭付近(既存の直近セッション節の上)に追加する。何を実装したか、ユーザーからの指示内容、変更したファイル、検証結果(`flutter analyze`/`flutter test`/`flutter run`の結果、ブラウザ目視確認の有無)を具体的に記述する。既存の節のスタイル(日付・タスクIDの見出し、実施内容の箇条書き)に合わせる。
   - タスクが未完了/失敗で終わった場合は、引き継ぎ内容(何が問題で、次に何を試すべきか)を明記する。
   - 「次回の着手点」節を、今回完了したタスクを踏まえて更新する(次に着手すべき依存関係の空いたタスクを反映)。
   - **本書は「直近1セッション分の作業ログ」だけを保つ(2026-07-29にトークン削減のため5件→1件へ変更)。** 新しい節を足す前に、いま載っている節を切り取って `docs/archive/NEXT_SESSION_log.md` の先頭(前書きの直後)へ節番号・本文そのまま移す。
   - 「1. 現状サマリ」に完了タスクを1行ずつ積み上げない(それはマスタープラン側の役目)。次回に効く制約・未解決事項だけを残す。
2. **`docs/改修マスタープラン.md` の進捗表を更新する**
   - §3 のタスク表で完了したタスク行は、**その行をそのまま `docs/archive/マスタープラン_完了タスク.md` の該当フェーズ節へ移し**(状態セルは `✅ <日付> <完了内容の要点>` にする)、本体の表からは削除して直後の「> **完了済み(N件)**: …」のID一覧に追記する(件数も更新)。本体の表には未完了行だけを残す。
   - §4(画面インベントリ)や §2(全体進捗サマリ)など、完了したタスクに応じて更新が必要な表があれば合わせて更新する。
3. **新しい教訓があれば `rules/lessons_archive.md` に追記し、`rules/verification.md` の「教訓インデックス」にも1行足す**
   - 全文は `rules/lessons_archive.md` の**末尾**に `### L<最大番号+1> <太字見出しと同じ文言>` + 空行 + 本文の形式で追記する。
   - `rules/verification.md` 側は該当カテゴリの節に `- L<番号> <見出し(76文字まで)>` の1行だけ足す(**本文は書かない**。ここが長くなると毎ループのトークンが増える)。
   - 既存の箇条書きの形式(**太字の見出し**: 内容の説明)に合わせる。すでに書かれている教訓と重複する場合は追記しない。
   - 「教訓」とは、今回の作業で判明した非自明な事実・ハマりどころ・回避策であり、単なる作業ログではない(作業ログは NEXT_SESSION.md 側)。
4. **`docs/` 配下の Cycle 連番が正しいことを確認する**
   - `docs/` と `docs/archive/` の既存 `cycle_<N>_*` フォルダの最大 N を確認し、今回新規に作成した(あるいはこれから作成する)ドキュメントフォルダの番号が重複・欠番なく連番になっているか確認する。ずれていれば修正する。
5. **その日に agy 委譲を行った場合、実績ログを転記する**
   - `.claude/agy_logs/ledger.tsv`(`.gitignore`対象で非コミット)の該当行を確認し、`docs/antigravity_delegation_design.md` §7 の表へ1行ずつ転記する(列: 日付 / タスクID / 役割 / モデル / exit / 所要 / 変更F数 / 判定 / 備考。ledger.tsv側の`timestamp`→日付、`task_id`→タスクID、`role`→役割、`model`→モデル、`exit_code`→exit、`duration_sec`→所要、`changed_file_count`→変更F数に対応)。
   - `判定`列(ledger.tsv の `verdict`)は起動時点では空欄のことがあるため、`/end`時点で採否(`ok`/`ng`/`fallback`)を判断して埋める。
6. **commit / push する**
   - まだコミットしていない変更があれば確認不要でコミットしてよい。**`git push` も、検証が完了していれば確認不要で実行してよい**(定義・詳細は下記「注意」および`CLAUDE.md`§日次改修ループ運用ルール参照)。「検証が完了」とは`verifier`が全項目パスを報告済み、またはコード変更を含まない(ドキュメント・設定のみ)こと。検証していない・NGのままの変更をpushする場合のみ、事前にチャットで許可を得る。
   - 直前の `git status` で意図しないファイルが混ざっていないか確認してからステージする。
7. **セッション継続 vs `/clear` を提案する**(`/loop`経由の無人実行時は行わない): `CLAUDE.md`§日次改修ループ運用ルール「セッション継続 vs `/clear` の判断」に従い、`loop_guard.js`の直近出力(本ループのcost/turns)を根拠に、次回`/start`・`/full_loop`をこのセッションのまま続けてよいか一言提案する。提案に留め、`/clear`の実行はユーザーに委ねる。

## 注意

- 手順は (a) NEXT_SESSION.md 更新 → (b) マスタープラン進捗表更新 → (c) commit/push の順を厳守する(`CLAUDE.md` の運用ルールに明記された順序)。
- コスト超過・失敗回数超過などの終了条件で停止する場合も、新規タスクには着手せずこの手順のみを実行する。
- **push・デプロイ・削除の確認ルールの定義・経緯・分類器ブロック時の対処は`CLAUDE.md`§日次改修ループ運用ルールが正本**(2026-07-25「push含め事前承認済み」という運用は2026-07-30に撤回済み。ハーネスの自動モード分類器はCLAUDE.mdの事前承認記述を有効な同意経路とみなさない設計のため)。検証未完了のpushは事前にチャットで許可を得る。ファイル・データの削除を伴う操作も都度一言説明してから実行し、分類器にブロックされた場合はサブエージェント委譲などで回避せずユーザーに説明して許可を得る。
