# full_loop — 選定〜実装〜デプロイ〜本番確認〜/end を一括実行する

`/start`(状況確認・候補提示のみ)と`/end`(締めの手順のみ)を、ユーザーの明示的な一括実行指示のもとで1回の指示で最後まで繋げて実行する「自動フルループ」モード。BeanBase 2.0 の「日次改修ループ」(`CLAUDE.md` §日次改修ループ運用ルール)の1ループ分を、着手確認を挟まずに完走させる。

## いつ使うか

ユーザーが以下のような**一括実行の明示的指示**をした場合に使う:
- 「依存がなく優先度が高いものから着手して」
- 「コストを気にせずひとつのタスクを一括で終わらせて」
- 「終わったらデプロイして本番環境確認してから/endして」

これらの指示が無い通常の`/start`実行では、このスキルを使わず`start`スキル(候補提示→ユーザーの着手承認待ち)を使うこと。**着手対象タスクの選定自体をユーザー承認なしで進めてよい、というのがこのスキル固有の許可**であり、コスト/ターン上限等の安全装置は通常運用と同じく効かせる。**2026-07-25のユーザー指示により、本番書き込み・デプロイ・pushを含め「ファイル削除以外はすべて事前承認済み」としてこのプロジェクトでは運用する(詳細は下記「注意」参照)。**

## 手順

1. **状況確認**(`start`スキルの手順1〜4と同じ): `git pull`→コンフリクトがあれば停止して報告。`.claude/loop_state.md`・`.claude/loop_failures.txt`でしきい値(コスト$24超/ターン30到達/連続失敗3回、2026-07-25〜いずれも直近の`/start`・`/full_loop`以降の1ループ単位で判定)超過を確認→超過していれば新規着手せずユーザーに報告して止まる。`NEXT_SESSION.md`の「次回の着手点」と`docs/改修マスタープラン.md` §3 のタスク表を読む。
2. **タスク選定**: 「依存が満たされた最上位のタスク」を1つ選ぶ。`NEXT_SESSION.md`の推奨と一致すればそれを採用。複数の無依存タスクがあればタスク表内で上にあるものを優先し、選定理由を一言でユーザーに共有してから実装に入る(この選定に限り承認を待たない)。**タスク文に「⚠️上位モデルで実施」「`full_loop`の自動選定対象外」等の注記があるタスクは選ばない**(2026-07-26のユーザー指示、`statistics_feature_design.md`§12①の「画面デザインの新規検討は上位モデルで実施」ルールに基づく除外。該当タスクのみが依存充足で残っている場合は、着手すべきタスクが無い場合と同様の扱い=ユーザー承認待ちにする)。
3. **実装**: `CLAUDE.md`の規約(全マスタータブへの一律適用、`[Antigravity]`ログ、外部データのID `.toString()`化、モデル追加時のシート列プロビジョニング漏れ対策など)に従う。統計解析・予測機能に触れる場合は同ファイル§統計解析・予測機能の実装ルールを厳守する。
4. **検証**(`rules/verification.md`準拠): `flutter analyze`(新規issue無し)→`flutter test`(全パス)→`flutter build web`成功。可能なら`build/web`をローカル配信し`claude-in-chrome`で実データに対しブラウザ確認する。
5. **デプロイ**(`docs/deploy.md`手順): `firebase deploy --only hosting`。GASスキーマの非破壊的変更(列追加等、`gas/Code.gs`の`EXISTING_SHEET_EXTRA_COLUMNS`経由)・本番Sheets/Driveへの実データ登録は確認不要で進めてよい(2026-07-25のユーザー指示、下記「注意」参照)。**本番データの削除を伴う場合のみ、実行前にユーザーへ一度確認する。**
6. **本番確認**: デプロイした`build/web`と同一の成果物をローカル配信(未使用ポート、Service Workerキャッシュ回避)し、本番GAS実データに対して新機能を`claude-in-chrome`で確認する。拡張が本番ドメインを直接ブロックする制約の回避策(`docs/deploy.md`記載)。
7. **`/end`の手順をそのまま実行**: (a) `NEXT_SESSION.md`更新(今回の実装内容・検証結果・本番確認結果・次回の着手点) → (b) `docs/改修マスタープラン.md`の進捗表更新(⬜→✅) → (c) 新しい教訓があれば`rules/verification.md`に追記 → (d) `docs/`配下のCycle連番確認 → (e) commit/push。

## `/loop`による定期実行時の追加ルール

このスキルを`/loop 1 full_loop`等で短い間隔の定期実行に用いる場合、手順1(状況確認)の前に以下を確認すること:

- **進行中のバックグラウンドタスクの確認**: 自分が過去のループ実行で起動したバックグラウンドタスク(Bashの`run_in_background`、Agentのバックグラウンド実行、`flutter build`/デプロイ等の長時間コマンド)が、起動から5分経っても完了していない場合は、新規タスクには着手せず、その進捗確認(状態の問い合わせ・完了待ち)のみを行って今回のループを終える。
- **着手すべきタスクが無い場合の承認待ち**: 進行中のバックグラウンドタスクが無く、かつ今回新たに着手できる/すべきタスクも無い場合は、新規タスクの着手前に必ずユーザーへ承認を求め、ユーザーの回答があるまで処理を開始しない。このスキル本来の「タスク選定はユーザー承認なしで進めてよい」という許可(手順2)は、定期実行によって無人のまま新規タスクを選び続けることを防ぐため、ここでは適用しない。**承認を求める際は`PushNotification`でも通知する**(cron定期実行はユーザーが画面を見ていない前提のため)。
- **セッションを軽量に保つ**: `/loop`による定期実行では、手順7(`/end`相当の締め)が完了した後、次回のループ起動前に`/clear`を実行してセッションのコンテキストをリセットする。次回起動時に必要な情報(進捗・引き継ぎ)は`NEXT_SESSION.md`・`docs/改修マスタープラン.md`・`.claude/loop_state.md`等ディスク上のファイルから毎回読み直すため、`/clear`で会話履歴を消してもループの継続に支障はない。新規タスクに着手せずユーザー承認待ちで今回のループを終える場合(上記2点)は、ユーザーへの質問がまだ残っている状態のため`/clear`を実行しない。

## 注意

- 終了条件(連続失敗3回・コスト$24超・ターン30到達)に達した場合は、実装途中でも直ちに手順7(引き継ぎ記載を優先した`/end`手順)に切り替えて停止する。新規タスクには着手しない。
- **確認不要の範囲(2026-07-25のユーザー指示「ファイル削除以外はすべて許可する、一度許可したものは以降すべて許可扱いにして確認を減らして」に基づく、このプロジェクト固有の運用)**: 本番Sheets/Driveへの実データ登録・更新、デプロイ(`firebase deploy`/`clasp push`・`clasp redeploy`)、pushは事前承認済みとして都度の確認なしに実行してよい。
- **確認が必要な範囲(唯一の例外)**: ファイル・データの**削除**を伴う操作(本番Sheets/Driveのレコード削除、`rm`/`git clean`等の破壊的ファイル操作、`git reset --hard`等)は、一括実行の指示があってもその都度リスクを一言説明してから実行する。
- **ユーザーへの依頼・確認は必ずプッシュ通知する(2026-07-25ユーザー指示)**: `AskUserQuestion`での質問、終了条件到達の報告、削除操作前のリスク説明など、ユーザーの反応・判断を待つ場面では`PushNotification`ツールでも同時に通知する(`CLAUDE.md`§日次改修ループ運用ルール参照)。
