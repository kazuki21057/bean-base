# token_review — 10回に1回のトークン節約見直し

## 目的・役割分担

**このスキルは「見直しをどう回すか」の手順書であり、調査も分析もこのスキル自身は行わない。** Web調査は`researcher`、本リポジトリ実測との突き合わせと採否判断は`architect`へ委譲する。親は起動判定・委譲・反映・記録のみを担う。

正本の関係: 節約計画と採否判断は`docs/token_optimization_design.md` §10が正本、実測の記録先は同§7(効果測定ログ)・§8(Proプラン使用率ログ)。運用ルール本体は`CLAUDE.md`§日次改修ループ運用ルール「トークン浪費の調査ルール」。**このスキルにそれらの内容を書き写さない**(委譲先に該当節を読ませる)。

## 起動条件

- `.claude/full_loop_run_count.txt`の値が**10の倍数**になった起動(`.claude/skills/full_loop/SKILL.md` 手順6.5から呼ばれる)。
- ユーザーが`/token_review`と明示的に呼んだ場合。
- **延期の判断**: 手順6.5で取得した使用率が高水準(目安: 5時間枠85%超、または週次90%超)なら**実行せず次回セッション冒頭へ延期**し、§8の当該ループ行に「延期した事実と理由」を書く(この分析自体が`researcher`+`architect`の2体を要するため。実績: 2026-08-14の10回目は5時間枠88%で延期)。

## 手順

1. **前提の確認(親、軽量)**: `grep -n "^### 10-" docs/token_optimization_design.md`で§10の最新の採否判断節を特定し、その節の「様子見」「再検討条件」だけを読む。条件を満たしたものがあれば今回の検討対象に含める。§10-4「採用しない選択肢」で決着済みの論点は蒸し返さない。

2. **Web調査フェーズ(`researcher`へ委譲、`run_in_background: false`)**: 以下のテンプレートの`<>`を埋めて渡す。

   > 「AIコーディングエージェント運用でのトークン/コスト節約テクニックをWeb調査し、`docs/research/<今日の日付>_token_saving_techniques.md`にレポートを保存してください。**報告・レポートとも日本語で書いてください。** 観点は(1)繰り返し読み込みのオーバーヘッド削減 (2)サブエージェント委譲のオーバーヘッド削減 (3)検証(テスト・ビルド)の繰り返しコスト削減 (4)その他一般的ベストプラクティス、の4つです。**既にこのリポジトリで採用済み・不採用決着済みの手法は対象外**なので、着手前に`docs/token_optimization_design.md`の§10-1〜§10-5(および§10以降に追加されている採否判断の節)を`Read(offset/limit)`で読み、そこに挙がっている手法と重複するものは『除外した手法』としてまとめるに留めてください。各手法には出典URLと取得日、報告されている効果、**このリポジトリへの適用可能性の初見**を必ず添えてください。裏が取れていない数値は『未確認』と明記してください。<今回特に知りたい論点があれば1〜2行で>」

3. **実測との突き合わせ・採否判断(`architect`へ委譲、`run_in_background: false`)**: `.claude/skills/full_loop/SKILL.md`の「architect委譲プロンプトのテンプレ」に従い、**読むべき正本ファイルを親が列挙して渡す**(最低限: 手順2の調査レポート、`docs/token_optimization_design.md` §7・§8・§10-1〜最新の採否判断節、`CLAUDE.md`の該当3節)。委譲プロンプトに次の4点を必ず含める。

   - 調査レポートの**各手法について「採用/様子見/不採用」を明示**し、判断基準は§10-4の考え方(このリポジトリの規模・運用形態に見合うか、一次情報の裏付けがあるか)を踏襲すること。
   - 判断は§7・§8の**実測と突き合わせて**行い、5時間枠と週次を**両方**見ること(片方だけで結論しない、`CLAUDE.md`のトークン浪費の調査ルール)。
   - **採用したものは、反映先(どのファイルのどの箇所に何を追記するか)と実際の追記文言まで確定**させること。implementerに設計判断をさせない粒度にする。
   - 結果を`docs/token_optimization_design.md`の**§10の新規節**(既存の最大節番号+1)として記録し、**「様子見」の再検討条件**を必ず節内に残すこと。

4. **反映フェーズ(親)**: 採用分を次の基準で振り分ける。

   | 反映のしかた | 条件 |
   |---|---|
   | このループ内で親が直接編集 | 1ファイル・目安10行以内の追記で、既存の恒久ルールの**緩和を伴わない**もの |
   | マスタープランへタスク起票(通常タスク・S) | 上記を超える反映。文言は手順3で確定済みのものをタスク行から参照させる |
   | ユーザー確認を完了条件に含めて起票 | `CLAUDE.md`の恒久ルール(モデル分担・確認ルール・委譲の必須性)の**緩和**、権限設定・デプロイに関わるもの |

   - **ID採番**: `grep -oE "T5-A[0-9]+" docs/改修マスタープラン.md | sort -t A -k2 -n | tail -1`で現在の最大値を確認し、その+1から連番で採る。**架空のIDを作らない。**
   - 行の書式は既存行に合わせ、完了条件の末尾に`／受入: 免除(ドキュメントのみ)`等の受入欄を付ける(T5-A71)。
   - **BOM・改行コードは既存ファイルのものを保持する**(`docs/改修マスタープラン.md`はCRLF、`docs/token_optimization_design.md`はLF、いずれもBOM無し)。

5. **記録**: §7・§8への本ループ実測の追記は`full_loop`手順6.5の通常記録として行う(**このスキルで二重に書かない**)。ただし§7の備考には「本ループでトークン節約見直しを実施した」旨と、起票したタスクIDを1行添える。採否判断そのものは手順3でarchitectが§10の新規節に記録済みであることを確認する。

## 注意

- **このスキル自身はコードもルールも書き換えない。** 反映は手順4の基準に従って親が行うか、後続タスクへ回す。
- 見直しの結論は必ず**このリポジトリの実測(§7・§8)**で裏付ける。外部記事の削減率(◯倍・◯%)をそのまま採用根拠にしない(§10-4の既存判断)。
- 採否が「様子見」で終わった手法は、**再検討条件を書かない限り記録しない**(条件の無い様子見は毎回同じ調査を繰り返す原因になる)。
